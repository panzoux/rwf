# Phase 7.9 — シンタックスハイライト（ビューア）: **不採用**

**決定日**: 2026-08-29
**決定**: `syntect` によるシンタックスハイライトを **実装しない**。Phase 7.9 をクローズする。
**状態**: ROADMAP の 7.9 行は `[-]`（不採用）。再着手する場合は本書「再検討の条件」を満たすこと。

---

## 1. 何を検討したか

ビューア（`rwf-bin/src/ui/viewer.rs` の `render_text_content`）に
`syntect` クレートでコードのシンタックスハイライトを載せる案（旧 7.6、twf にない機能）。

検討にあたり実際に依存を追加してリリースビルドし、サイズを実測した
（測定用の変更はすべて revert 済み。ツリーに `syntect` は残っていない）。

---

## 2. 調査で判明した事実

### 2.1 外部ファイルは不要（＝サイズ問題の本体ではない）

`syntect` 5.3 は構文定義・テーマを **圧縮ダンプとして `include_bytes!` でバイナリに埋め込む**。

```
~/.cargo/registry/src/*/syntect-5.3.0/assets/
  default_newlines.packdump   368,467 B   ← 75 構文
  default.themedump             5,035 B   ←  7 テーマ
```

実行時に `SyntaxSet::load_defaults_newlines()` / `ThemeSet::load_defaults()` が
`syntaxes=75 themes=7` を返すことをプローブビルドで確認済み。
`.sublime-syntax` / `.tmTheme` を配布・インストールする必要は**ない**
（ユーザー拡張を許したい場合のみ `yaml-load` / `plist-load` を足す — 本決定とは独立）。

### 2.2 バイナリサイズ実測（`i686-pc-windows-msvc`, release, デフォルトプロファイル）

| ビルド | `rwf.exe` | 差分 |
|---|---:|---:|
| `main` 現状（基準） | 7,269,888 B | — |
| `+ syntect` `default-fancy`（純 Rust） | 7,957,504 B | **+687,616 B（+672 KB, +9.5%）** |
| `+ syntect` `default-onig`（C 製 oniguruma） | 8,292,864 B | +1,022,976 B（+999 KB, +14%） |

**単体プローブでの計測は逆の結論を出すので注意**。空クレートに足すと `onig` の方が
`fancy-regex` より約 940 KB 小さい。しかし rwf は既に `regex`（→ `regex-automata` /
`regex-syntax`）をリンクしており、`fancy-regex` はそれを再利用して安く済むのに対し、
`onig` は何も共有しない C ライブラリを丸ごと持ち込む。**実バイナリで測ること。**

→ 仮に採用するなら選択は `default-features = false, features = ["default-fancy"]`
（rwf 内では小さく、純 Rust、CI に C ツールチェーン不要、FFI 面も増えない）。

### 2.3 決め手となったアーキテクチャ上の非適合

- **rwf のビューアはランダムアクセス**: `render_text_content` は `viewer.line_offset` から
  ビューポート高さ分の行だけをデコードする。100 MB 超は `SeekableFile::read_bytes` で
  必要な範囲のみ seek + read（Phase 6.6/6.7 で mmap を廃してまで確立した設計）。
- **syntect のパーサは逐次かつステートフル**: 複数行文字列・ブロックコメント・ヒアドキュメントが
  あるため、50,000 行目の色を正しく決めるには 0..49,999 行目をパースし終えている必要がある。

この 2 つは正面から衝突する。埋めるには「N 行ごとに `ParseState` のチェックポイントを取り、
ジャンプ時は直近のチェックポイントから再開する」機構＋その破棄ポリシーが要る。
加えて描画層で I/O・重処理を行わない原則（`docs/ARCHITECTURE.md`）により、
ハイライトはワーカープールの `Job` 化とキャッシュが前提になる。

---

## 3. 不採用の理由

**ビューアの中核価値は「大きなファイルが即座に開くこと」であり、syntect はその作りになっていない。**

- 全文を先頭から通すか、チェックポイント機構を作り込むかのどちらかが必須で、
  前者は「即座に開く」を壊し、後者は 7.9 の見積 2 週間の大半を占める複雑度をビューアの
  ホットパスに恒久的に持ち込む。
- 得られるものは表示上の装飾にとどまり、ファイラのビューアとしての用途（ログ・データ・
  巨大ファイルの確認）とは価値の方向が合わない。
- 672 KB のバイナリ増自体は許容範囲だが、**サイズは判断理由ではない**。理由は上記の設計非適合。

**代替**: コードをハイライト付きで読みたい場合は、外部エディタ／ビューア（Phase 6.2 の
`extension_associations.json`、Phase 7.3 のスマート・ファイルオープナー）で開く。
rwf は「開くべきツールへ渡す」ことを既にファーストクラスで支援しており、そちらが正しい担当。

---

## 4. 再検討の条件

次のいずれかが変われば、本決定は見直す価値がある。

1. ビューアが「小さいファイルは全文インメモリ」という前提を強く持つモードを別途持ち、
   ハイライトをそのモード限定（例: 1〜2 MB 以下）に閉じ込められると判断したとき。
2. ランダムアクセスに適した（＝任意行から状態復元できる）ハイライトエンジンが選択肢に入ったとき。
3. ユーザーから実使用に基づく具体的な要望が出たとき（現時点では推測ベースの機能）。

いずれの場合も、**まず 2.3 のチェックポイント設計に答えを出してから**着手すること。
依存の選定（2.2）は解決済みなので繰り返さなくてよい。
