## 1. 背景・問題定義

### 現状の rwf ビューア（Phase 4.3 + 今セッション修正後）

| ファイルサイズ | 方式 | 問題 |
|---|---|---|
| ≤ 100 MB | `std::fs::read()` → `FileBytes::InMemory(Vec<u8>)` | なし（スナップショット取得、安全） |
| > 100 MB | `memmap2::Mmap` → `FileBytes::Mapped(Mmap)` | **レンダリング時にUIスレッドからmmap読み込み → ページフォルト遅延の可能性** |

InMemoryパスは今セッションで修正済み（`spawn_blocking`内でファイル全体を読む）。  
mmap パスはオープン・インデックス構築は `spawn_blocking` に移行済みだが、レンダリング時の読み込みはUIスレッド上で行われ、活発に書き込まれているファイルではページフォルト遅延が発生しうる。

### twf の解法（LargeFileEngine.cs）

twf はファイルサイズを問わず `FileStream` + `Seek + Read` を採用する。mmap を一切使わない。

```csharp
// FileShare.ReadWrite: 他プロセスが書き込み中でもオープン可能
_fileStream = new FileStream(
    _filePath, FileMode.Open, FileAccess.Read,
    FileShare.ReadWrite, BufferSize /* 64KB */);

// レンダリング時: 表示に必要な範囲だけ Seek + Read
lock (_streamLock)
{
    _fileStream.Seek(startOffset, SeekOrigin.Begin);
    _fileStream.Read(buffer, 0, length);
}

// インデックス構築: 専用の別 FileStream で独立して実行（Task.Run）
using (var fs = new FileStream(_filePath, ..., FileShare.ReadWrite, BufferSize))
{
    while ((bytesRead = fs.Read(buffer, 0, buffer.Length)) > 0) { ... }
}
```

**ポイント**:
- `FileShare.ReadWrite` → 他プロセスが書き込み中のログファイルをオープン可能
- `Seek + Read` → ページフォルトなし（mmap と異なり OS ページキャッシュを直接触らない）
- ビューポートが必要な範囲だけ読む → メモリ使用量は定数（ファイルサイズによらない）
- インデックス構築とビューポート読み込みはそれぞれ別の FileHandle → 競合なし

## 2. rwf への適用設計

### 2.1 対象範囲

**変更対象**: `FileBytes::Mapped(Mmap)` → `FileBytes::Seekable(...)` への置き換え  
**非変更**: `FileBytes::InMemory(Vec<u8>)` は ≤ 100 MB で引き続き使用（完璧に動作している）

新しいサイズ分岐:

| ファイルサイズ | 方式 |
|---|---|
| ≤ 100 MB | `FileBytes::InMemory(Vec<u8>)`（現状維持） |
| > 100 MB | `FileBytes::Seekable(SeekableFile)` ← **新規** |

### 2.2 SeekableFile 構造体

```rust
/// ファイルへのシーク+読み込みアクセス（mmap不使用）
pub struct SeekableFile {
    /// レンダリング用ファイルハンドル（seek+readに使用）
    /// Arc<Mutex<...>> で UI スレッドとビューポートキャッシュ更新スレッドが共有
    file: Arc<Mutex<std::fs::File>>,
    pub size: u64,
    /// デコード済み行のビューポートキャッシュ
    /// 直近の GetTextLines 結果を保持し、同一範囲の再描画を高速化
    viewport_cache: Arc<Mutex<ViewportCache>>,
}

struct ViewportCache {
    start_line: usize,
    lines: Vec<String>,          // デコード済み文字列
    encoding: TextEncoding,
}
```

### 2.3 FileBytes の変更

```rust
pub enum FileBytes {
    InMemory(Vec<u8>),
    Seekable(SeekableFile),   // ← Mapped(Mmap) を置き換え
}

impl FileBytes {
    pub fn len(&self) -> usize {
        match self {
            Self::InMemory(v) => v.len(),
            Self::Seekable(s) => s.size as usize,
        }
    }

    pub fn as_bytes(&self) -> &[u8] {
        match self {
            Self::InMemory(v) => v.as_slice(),
            // Seekable は直接スライスを返せない → レンダリング側で GetTextLines を使う
            Self::Seekable(_) => unreachable!("Use get_text_lines() for Seekable files"),
        }
    }

    /// テキストビューア用: startLine から count 行取得
    pub fn get_text_lines(
        &self, start_line: usize, count: usize,
        line_index: &LineIndex, encoding: TextEncoding,
    ) -> Vec<String> { ... }
}
```

### 2.4 インデックス構築（execute_load_file_for_viewer の変更）

大容量ファイルのパス:

```rust
} else {
    // > 100 MB: Seekable モード
    // インデックス用に別ハンドルでファイルを開く（rwf は Windows デフォルトで
    // FILE_SHARE_READ | FILE_SHARE_WRITE のため concurrent write 可能）
    let file_for_render = std::fs::File::open(&path_for_open)?;
    let size = meta.len();
    let seekable = SeekableFile::new(file_for_render, size);

    // エンコーディング検出: 先頭 16KB を読んで判定
    let sample = seekable.read_bytes(0, 16384.min(size as usize))?;
    let encoding = TextEncoding::detect(&sample);

    Ok((FileBytes::Seekable(seekable), encoding, None))
}
```

インデックス構築ループも同様に `spawn_blocking` で別ハンドルを開いて実行（現行コードと同じ構造を維持）。

### 2.5 レンダリング側の変更（ViewerBuffer の GetLines）

**現状**: テキストレンダラーが `buffer.bytes.as_bytes()` で `&[u8]` を取得し、LineIndex のオフセットでスライス

**変更後**: `FileBytes::Seekable` の場合は `get_text_lines(start_line, viewport_height, ...)` を呼ぶ

レンダリングは Tokio 非同期スレッド上で実行されるため、`get_text_lines` 内の `File::seek + read` は **`spawn_blocking` でラップ** するか、専用の読み込みスレッドを立てる。

#### オプション A: spawn_blocking ラップ（シンプル、推奨）

```
render() {
    match buffer.bytes {
        InMemory(v) → &v[offset..] (即時)
        Seekable(s) → spawn_blocking(|| s.read_viewport(start, count)).await
    }
}
```

各フレームで `spawn_blocking` を呼ぶのは重く見えるが、実際は:
- Tokio ブロッキングスレッドプールは UI から独立
- ビューポートは数KB〜数十KB 程度なので IO は < 1ms（ローカルファイル）
- ビューポートキャッシュを挟めば同一範囲の再描画は spawn_blocking を呼ばない

#### オプション B: 専用リーダースレッド（twf 方式に最も近い）

```
std::thread::spawn("viewer-reader") {
    // 永続ループ
    loop {
        let req = rx.recv(); // ReadRequest { start_line, count }
        let lines = file.seek_and_read(...);
        tx.send(ReadResult { lines });
    }
}
```

UI は `tx.send(req)` → 次フレームで `rx.try_recv()` で結果取得（ノンブロッキング）。  
結果が未着なら前フレームのキャッシュを表示し続ける → ちらつきなし。

**推奨**: まずオプション A で実装（シンプル）。ネットワークファイル対応時にオプション B へ昇格。

## 3. ネットワークファイル対応との関係

この設計は将来の 7.8 SSH/SFTP 対応の基盤になる。

`SeekableFile` の `file` フィールドを `ReadAt` トレイトに抽象化することで:
- ローカル: `std::fs::File` の `seek + read`
- SFTP: `ssh2::Sftp::open` の `read_at`

の両方を同じレンダリングコードで扱える。mmap はネットワーク越しには使えないため、このリファクタリングは SFTP 対応の前提条件になる。

## 4. 現状との比較

| 観点 | 現状（mmap > 100MB） | 6.7 実装後（Seekable） |
|---|---|---|
| 活発な書き込みファイルのオープン | ✅ spawn_blocking | ✅ spawn_blocking |
| インデックス構築 | ✅ spawn_blocking | ✅ spawn_blocking |
| レンダリング時 IO | ⚠️ UIスレッドでmmap読み（ページフォルト危険） | ✅ spawn_blocking / リーダースレッド |
| メモリ使用量 | ファイル全体をmmap（VMアドレス消費） | ビューポート分のみ（< 1MB） |
| ネットワークファイル | ❌ 不可（mmap はローカル専用） | ✅ 将来の `ReadAt` 抽象化で対応可 |
| ファイルサイズ上限 | RAM/VMアドレス空間に依存 | 上限なし |
| ランダムジャンプ速度 | 即時（アドレス演算のみ） | < 1ms（ローカル SSD）|

## 6. twf との実装差異

| 観点 | twf (C#) | rwf (Rust) |
|---|---|---|
| FileShare 設定 | `FileShare.ReadWrite` 明示指定 | Windows デフォルトで `FILE_SHARE_READ \| FILE_SHARE_WRITE` — 同等 |
| スレッド方式 | `Task.Run`（.NET ThreadPool） | `spawn_blocking`（Tokio blocking pool）|
| ロック方式 | `lock (_streamLock)` | `Arc<Mutex<File>>` |
| サイズ閾値 | なし（全ファイル LargeFileEngine） | InMemory ≤ 100MB を維持（スナップショット安全性のため） |
| バッファサイズ | 64 KB | 同等（調整可） |
