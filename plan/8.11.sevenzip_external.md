# 8.11 7-Zip ライブラリ（7z.dll / 7z.so）によるアーカイブ形式拡張

**状態**: `[ ]` 実装中（2026-11-28 起票・実装。ブランチ `feat/8.11-7zip-lib`。残りは CI（Linux）と実機確認）
**Kanban**: #30
**由来**: ROADMAP「Future Enhancement Candidates」Phase 8.11。5.3（RAR）・5.5（LZH）は「5.6 libarchive 経由で実装予定」のまま止まっている。

## 1. 目的と方針

**7-Zip のライブラリ（Windows は `7z.dll`、Linux/macOS は `7z.so`）を読み込んで、扱えるアーカイブ形式を一気に広げる。**

- 理由: 純 Rust のクレートは更新が止まっているか（rwf が使う `sevenz-rust` 0.6 も後継の `sevenz-rust2` に移っている）、対応形式が狭い。
  7-Zip は RAR/RAR5、LZH、ARJ、CAB、CHM、CPIO、WIM、XZ、ZSTD、ISO、7z、zip、tar … を 1 つのライブラリで読める（`7z i` で確認）。
- **7-Zip ライブラリがある環境では、7-Zip が開ける形式はすべて 7-Zip を優先する**（zip / 7z / tar / iso も含む）。
- **無い環境では今の内蔵ハンドラ（zip / 7z / tar / iso）にフォールバック**。LZH などはエラー表示（今と同じ）。
- **Linux / macOS では、RAR を `unrar-ng`（UnRAR の C++ ソースを静的リンク）で補う**（§8-4 の決定）。7-Zip が無い時と、7-Zip が「未対応の方式」と返した時（Linux / macOS の 7z.so には RAR デコーダが無い、§2.7・§2.9）に使う。
- **Windows には `unrar-ng` を入れない**（`[target.'cfg(not(windows))'.dependencies]`）。Windows の 7z.dll は RAR を展開できるので、7-Zip があれば足りる。7-Zip が無い Windows では RAR も「7-Zip が必要です」になる。Windows のビルドに C++ のコンパイルが増えない。
- 外部プロセス（`7z.exe`）は起動しない。libarchive（5.6）は使わない。
- やらないこと（v1）: 7-Zip 経由の**作成・更新**（`IOutArchive`）、パスワード入力 UI。作成は今の内蔵（zip / 7z / tar）のまま。

| 環境 | zip / 7z / tar / iso | RAR / LZH / ARJ / CAB / WIM … |
|---|---|---|
| 7-Zip ライブラリあり | **7-Zip**（開けなければ内蔵） | **7-Zip**（Linux / macOS で RAR を展開できなければ `unrar-ng`） |
| なし | 内蔵（今と同じ） | Linux / macOS の RAR は `unrar-ng`。それ以外（Windows の RAR を含む）はエラー「7-Zip が必要です」 |

### 1.1 採らなかった案

| 案 | 採らない理由 |
|---|---|
| `7z.exe` を起動 | 実測で 1 回約 25 ms（§2.1）。階層を移動するたびに一覧を取り直すので、毎回このコストを払う |
| libarchive（5.6、`compress-tools`） | Windows では C ライブラリのビルドと配布（vcpkg 等）が重い。対応形式も 7-Zip の方が広い → **不採用へ移す** |
| 形式ごとに純 Rust クレートを足す（`delharc` 等） | 形式ごとに依存が増え、更新が止まりやすい。範囲も狭い。7-Zip が無い環境向けの補助として後で検討する余地だけ残す（§8-3）。例外は RAR の `unrar-ng`（7z.so だけでは RAR を展開できない環境があるため、§2.9） |
| Debian の `Codecs/Rar.so` を 7-Zip に渡す | そのままだと segfault する（Debian 自身の `7z` も落ちる）。避けるには 7-Zip の内部関数 `CrcGenerateTable` を呼ぶ必要がある。segfault は rwf ごと落ちるので、非公開の関数に頼る方法は採らない（§2.9） |

## 2. 観測（2026-11-28、このマシン）

### 2.1 7z.exe の起動コスト（Windows）

`7z.exe l` を 20 回連続実行した平均: **24.6 ms**。書庫を指定しない `7z i` でも 23.2 ms、`cmd /c exit` だけで 18.3 ms → ほぼ全部がプロセス生成のコスト。キャッシュが温まった状態での値で、Defender のスキャンが入るとさらに増える。

### 2.2 Linux / macOS で 7z.so が手に入るか

- Debian/Ubuntu: `7zip` パッケージが `/usr/lib/7zip/7z.so` を入れる。RAR は `7zip-rar` が `/usr/lib/7zip/Codecs/Rar.so` を追加する。
- Homebrew（macOS / Linux）: `sevenzip` formula が `7zz` に加えて `Format7zF` から `lib/7z.so`（`lib7z` へのシンボリックリンク付き）をビルドして入れる。
- 7-zip.org 公式の Linux/macOS 版 tarball は「console version」とだけ書かれていて、`.so` を同梱するかは**未確認**。
- 出典: packages.debian.org の 7zip / 7zip-rar ファイル一覧、homebrew-core `Formula/s/sevenzip.rb`（2026-11-28 時点）。

### 2.4 ローカルの rwf は 32 ビット

ローカルの rustc の host は `i686-pc-windows-msvc` で、`target/debug/rwf.exe` は PE32（i386）。CI（`windows-latest`）は x64。
**DLL は呼び出し側とビット数が一致しないと読み込めない** → 32 ビットの rwf からは `C:\Program Files\7-Zip\7z.dll`（x64）は使えない。

**解決済み（2026-11-28）**: 32 ビット版の Rust 1.92 MSI をアンインストールし、rustup で `1.92.0-x86_64-pc-windows-msvc` を既定に設定した（CI と同じ版）。
x64 でのビルド（`rwf.exe` は PE32+ x86-64）、`fmt --check`、`clippy -D warnings`、`cargo test -p rwf`（394+5+10 passed）、`cargo test -p rwf-lib`（1631+5 passed、1 ignored）は通過済み。

### 2.6 Linux / macOS 版の ABI（7-Zip ソース `ip7z/7zip` main で確認。実機は未確認）

- 呼び出し規約: 非 Windows では `STDMETHODCALLTYPE` は空 → 普通の C の規約。Rust の `extern "system"` は非 Windows で `"C"` と同じなので、コードはそのままでよい。
- GUID は 16 バイトで同じ形。HRESULT の値も同じ（`S_OK`, `E_NOINTERFACE`, `E_ABORT` …）。
- **`IUnknown` の仮想デストラクタ**: v23 以降は既定で**無い**（`Z7_USE_VIRTUAL_DESTRUCTOR_IN_IUNKNOWN` はコメントアウト）。**v22 以前と p7zip には有る** → vtable の Release の後ろに 2 スロット増え、Read / Open などの位置がずれる。
  - 対応: 7-Zip 23 以降だけを対象にする（v23 以降は `GetModuleProp` を export しているので、それで判別）。古い版は「7-Zip 23 以降が必要」としてスキップ。Debian 12 の `7zip` は 22.01 なので対象外になる（Debian 13 / Ubuntu 24.04 以降と Homebrew は 23 以降）。
- **BSTR**: `wchar_t`（Linux/macOS は 4 バイト）の配列で、前に 4 バイトのバイト長が付く。確保は `malloc`、解放は `free(ptr - 4)`。試作の非 Windows 側はこの前提で書いてある。
- **PROPVARIANT は 16 バイト**（Windows x64 は 24 バイト）。1 個ずつ受け取るだけなら大きめのバッファでも問題ないが、型は cfg で分ける。
- 7-Zip 側の参照カウントは既定で非アトミック → 1 つの書庫オブジェクトを複数スレッドから同時に触らない（ワーカー 1 ジョブ = 1 オブジェクト）。

同じ試作コード（PROPVARIANT のサイズだけ cfg で切替）を 4 環境で実行した。

| 環境 | 7-Zip | ABI（GetModuleProp） | 形式数 | RAR 一覧 | RAR 展開 | LZH | 日本語 zip |
|---|---|---|---|---|---|---|---|
| windows-latest | 同梱の 7z.dll | 仮想デストラクタなし | 60 | OK | **OK** | OK | OK |
| ubuntu-24.04（apt `7zip` + `7zip-rar`） | 23.01+dfsg | なし | 59 | OK | **NG**（opRes=1 未対応の方式） | OK | OK |
| ubuntu-latest（Homebrew `sevenzip`） | 26.06 | なし | 60 | OK | **NG**（同上） | OK | OK |
| macos-latest（Homebrew `sevenzip`） | 26.06 | なし | 60 | OK | **NG**（同上） | OK | OK |

- **Linux / macOS でも ABI は想定どおり**。同じコードで読み込み・形式列挙・Open・一覧・展開が動いた（Windows 版との違いは PROPVARIANT のサイズだけ）。
- **RAR の展開だけが Linux / macOS で失敗**。一覧は取れる（RAR のハンドラはある）が、展開に必要な RAR の**デコーダ**が 7z.so に入っていない:
  - Homebrew: formula が `make ... DISABLE_RAR_COMPRESS=1` でビルドしている（`Formula/s/sevenzip.rb` 28・36 行目）。RAR デコーダは**どこにも無い**。
  - Debian/Ubuntu: RAR デコーダは別ファイル `/usr/lib/7zip/Codecs/Rar.so`。7z.so は自分では読み込まない。`7z` コマンドは、このファイルを読み込んで書庫オブジェクトに `ISetCompressCodecsInfo` で渡している（**rwf 側でも同じことをすれば使えるはず。未検証**）。
- 時刻: RAR4 の DOS 時刻は、実行環境のタイムゾーンで UTC に変換される（JST の手元では `04:43:22Z`、UTC のランナーでは `13:43:22Z`）。LZH レベル 2 の UTC 時刻はどこでも同じ。→ 7-Zip の時刻はそのまま使ってよい。

### 2.8 RAR 専用の代替: `unrar-ng`（x64 で再試験）

x64 に切り替えた後、`unrar-ng` 0.7.7（RAR 公式の UnRAR ソースを C++ で静的リンク）で `editd169e.rar` を一覧・全件展開できた（合計 620,474 バイト = 各ファイルのサイズの合計）。i686 でのリンク失敗は 32 ビット環境だけの問題だった。Linux / macOS では未試験。

### 2.9 Linux / macOS の RAR 展開の試作（§8-4 の決定を受けて。run 46092158246 / 46092417081 / 46092666727、2026-11-28）

| 環境 | 7-Zip のみ | `Codecs/Rar.so` を渡す | `Rar.so` ＋ `CrcGenerateTable` 呼び出し | `unrar-ng` |
|---|---|---|---|---|
| windows-latest | OK | （Codecs フォルダ無し） | — | OK |
| ubuntu-24.04（apt） | NG（opRes=1） | **segfault** | **OK**（6 件・全バイト一致） | OK |
| ubuntu-latest（Homebrew） | NG | （Codecs フォルダ無し） | — | OK |
| macos-latest（Homebrew） | NG | （Codecs フォルダ無し） | — | OK |

- **`Codecs/Rar.so` の受け渡し自体は動く**。`ISetCompressCodecsInfo` で渡すと、7z.so は `GetNumMethods` / `GetProperty` で Rar1/2/3/5 を読み取り、展開時に `CreateDecoder` を呼んでくる。
- **ただし Debian 23.01+dfsg-11 の Rar.so はクラッシュする**。最初の 2 ファイルは展開できるが、3 つ目の `editdisk.exe` で segfault になる（gdb: `NRar3::CProgram::PrepareProgram` → `CrcCalc` → アドレス 0 を呼ぶ）。
  - 原因: RAR3 の VM フィルタ（exe 用の E8 変換）が CRC を使う。ところが Rar.so は自分の CRC 関数ポインタ `g_CrcUpdate` を初期化していない。
  - **Debian 自身の `7z t editd169e.rar` も同じく segfault する** → rwf 側の不具合ではなく、パッケージの不具合。
  - Rar.so は `CrcGenerateTable` をエクスポートしている（`nm -D`）。**読み込み直後にこれを呼べば全件展開できた**。ただしこれは 7-Zip の内部関数で、公開 API ではない。
  - segfault はプロセスごと落ちるので、rwf 側では捕まえられない。
- **`unrar-ng` は 4 環境すべてで全件展開できた**（Homebrew の Linux / macOS でも、C++ のビルドを含めて問題なし）。

## 3. 構成

- 新クレート `rwf-7zlib`。`rwf-winmenu` と同じく unsafe をここに閉じ込める（`unsafe_code` の allow はこのクレートだけ。unsafe ブロックには `// SAFETY:` を付ける）。
- `libloading` で**実行時に**読み込む。リンク時の依存にはしない → 7-Zip が無い環境でもビルド・起動できる。
- rwf-lib 側に `SevenZipLibArchiveHandler`（`ArchiveHandler` を実装）を追加し、`MultiFormatArchiveHandler` の先頭に置く。
- RAR（Linux / macOS のみ、`#[cfg(not(windows))]`）: 今の `unsupported_handler!` の RAR スタブを、`unrar-ng` を使う `RarArchiveHandler` に置き換える。Windows は今のスタブのまま（エラー文言を「7-Zip が必要です」にする）。7-Zip で開けない時、または展開で「未対応の方式」（opRes=1）が返った時はこちらに回す。
  - `unrar-ng` 0.7.7（ラッパーは MIT OR Apache-2.0）。中身の UnRAR ソースは独自ライセンス（`vendor/unrar/license.txt`）: RAR の展開には自由に使える。RAR 互換の圧縮を作ることは禁止。改変して配布する時はライセンスの一節を同梱する。rwf は RAR を作らないので問題ない。ただし GPL とは両立しないので、rwf を将来 GPL にするなら見直す（今の rwf にはライセンスの指定が無い）。
  - Linux / macOS のビルドに C++ のコンパイルが入る（`cc` クレート。CI の既定コンパイラで通った）。

## 4. 検出（遅延・ワーカー側）

- 解決順: ① `config.json` の `Archive.SevenZipLibrary`（PascalCase、`#[serde(default)]`。空なら無視） → ② 既定の場所
  - Windows: `%ProgramFiles%\7-Zip\7z.dll`、`%ProgramFiles(x86)%\7-Zip\7z.dll`（rwf と同じビット数のものだけ使う。合わなければスキップしてログに残す）
  - Linux: `/usr/lib/7zip/7z.so`、`/usr/lib64/7zip/7z.so`、`/usr/libexec/7zip/7z.so`（p7zip の `/usr/lib/p7zip/7z.so` は旧 ABI なので探さない。`SevenZipLibrary` で指定しても「7-Zip 23 以上が必要」で弾く）
  - Homebrew: `/opt/homebrew/lib/7z.so`、`/usr/local/lib/7z.so`、`/home/linuxbrew/.linuxbrew/lib/7z.so`
- **最初に必要になった時にワーカー内で読み込み、`OnceLock` に保持**する（起動時に先回りしない）。設定をリロードしたら、次に使う時に解決し直す。
- 読み込み後に `GetNumberOfFormats` / `GetHandlerProperty2` で**形式と拡張子の一覧**を取り、どの形式を 7-Zip に回すかはこの一覧で決める。

### 4.1 入力スレッドとの関係

`MultiFormatArchiveHandler::new()` と `is_archive` は入力スレッドからも呼ばれる（`input/mod.rs:258, 355`）ので、**ここでは DLL を読まない・ファイルシステムに触れない**（IMPLICIT_CONTRACTS §8）。

- `is_archive` は拡張子だけで判定する。対象は「内蔵の拡張子」＋「7-Zip が通常扱う拡張子の固定表」（rar, lzh, lha, arj, cab, chm, cpio, wim, xz, zst …）。
- 7-Zip が無い環境でそれらに入ると、ワーカーが「7-Zip が必要です」とエラーを返す（Linux / macOS の RAR は `unrar-ng` で開く）。
- 重複している `input/mod.rs:21` の `is_archive()` は、この表を参照する形に一本化する。

## 5. 使う 7-Zip API

- エクスポート関数: `CreateObject`、`GetNumberOfFormats`、`GetHandlerProperty2`。
- 呼び出す側: `IInArchive`（`Open` / `GetNumberOfItems` / `GetProperty` / `Extract` / `Close`）。
- Rust で実装する COM オブジェクト: `IInStream`（ファイルの読み出し）、`IArchiveOpenCallback`、`IArchiveExtractCallback`、`ISequentialOutStream`、`ICryptoGetTextPassword`。
  - v1 の `ICryptoGetTextPassword` は空パスワードを返す → 暗号化書庫は「パスワード付きは未対応」で失敗させる。
- キャンセル: callback から `E_ABORT` を返す（`CancellationToken` を見る）。
- 一覧: `kpidPath` / `kpidIsDir` / `kpidSize` / `kpidMTime` / `kpidAttrib` を取り、`inner_path` の直下だけを `FileEntry` にする。ディレクトリ行が無い書庫は、パスから中間ディレクトリを作る。
- 展開: 単一ファイル、全体、サブディレクトリ（対象の index だけ渡し、出力パスから `inner_path` の分を取り除く）。

## 6. 時刻の扱い

- rwf 内部の `SystemTime` は**瞬間**（タイムゾーンに依存しない）。画面に出す時に `chrono::Local` に変換している（`rwf-bin/src/ui/panes.rs:534`）。NTFS も UTC で記録していて、表示の時にローカル時刻にしている。
- 7-Zip は `kpidMTime` を FILETIME（UTC）で返すので、そのまま使えばよい（DOS 時刻の形式も 7-Zip 側で変換済み）。
- **既存のバグ（コードを読んだ範囲。未実測）**: 内蔵の zip ハンドラ `zip_datetime_to_system_time`（`archive.rs:57`）は DOS 時刻（ローカルの壁時計）を UTC として解釈している → JST の環境では画面上 9 時間進んで見えるはず。7-Zip が無い環境では内蔵 zip が使われるので、この項目で一緒に直す。

## 8. 決めてほしいこと

1. ~~ローカルの 32 ビット toolchain は意図したものか~~ → 意図していなかったので x64 に統一した（2026-11-28）。
2. **7-Zip がある時、zip / 7z / tar / iso も 7-Zip を優先してよいか**（本計画の前提）。内蔵との差（表示される項目、エラー文言）が出たら、7-Zip 側に合わせる。

3. **7-Zip が無い環境での LZH**: エラー表示のままでよいか、補助として `delharc`（LZH、動作確認済み）も入れるか。
   - **決定（2026-11-28）: エラー表示のまま**（`delharc` は入れない）。（RAR は §8-4 で、Linux / macOS だけ `unrar-ng` で読めるようにする）
4. **Linux / macOS の RAR 展開**（§2.7）: 7z.so だけでは RAR を展開できない環境がある。案:
   - (a) Debian/Ubuntu: `Codecs/Rar.so` を読み込んで `ISetCompressCodecsInfo` で渡す（7-Zip の経路のまま。要試作）
   - (b) Homebrew・macOS: 7z.so に RAR デコーダが無いので、7-Zip の経路では手段が無い。RAR だけ `unrar-ng` で補う（x64 Windows で動作確認済み）か、「RAR は展開できない」と表示するか
   - 推奨: (a) を実装し、(b) は `unrar-ng` で補う。どちらも「7-Zip が未対応の方式と返した RAR だけ」に使う。
   - **決定（2026-11-28）: (a) + (b)**。(a) の `Codecs/Rar.so` 読み込みと、Linux / macOS での `unrar-ng` を試作で確かめる（§2.9）。
   - **再決定（2026-11-28）: (a') `unrar-ng` に一本化**。Rar.so は使わない。**`unrar-ng` は Windows 以外だけに入れる**（Windows は 7z.dll で RAR を展開できる。7-Zip が無い Windows の RAR はエラーのまま）。
   - 経緯 — **試作の結果（§2.9）、(a) の前提が崩れた**: Debian の Rar.so は、内部関数 `CrcGenerateTable` を呼ばないとプロセスごと落ちる。見直しの案:
     - (a') Rar.so は使わず、7-Zip が未対応と返した RAR（実際には Linux / macOS。Windows の 7z.dll は RAR を展開できる）と、7-Zip が無い環境の RAR を `unrar-ng` に回す（推奨。4 環境で動作確認済み。非公開シンボルに頼らない）
     - (a'') Rar.so を使う。ただし `CrcGenerateTable` がエクスポートされている時だけ、読み込み直後に呼ぶ。無ければ Rar.so は使わない（Debian で `unrar-ng` を足さずに済むが、将来の Rar.so で別の初期化漏れがあれば rwf が落ちる）
