# Phase 7.6 — トランザクション・ロールバック（Undo/Redo）

**作成日**: 2026-06-01  
**状態**: 設計改訂（2026-07-28、Operation Report 中心へ転換 — UI/UX の正は [7.6.operation_report_ui.md](7.6.operation_report_ui.md)）・着手保留（前提操作の実装が先）  
**対象**: ファイル操作の安全な取り消し、操作ミスのリカバリ

---

## 1. 目的

ファイル操作（移動、名前変更、削除等）の結果を、整合性を保ちながら安全に取り消す（Undo）機能を提供する。単純な「時間の巻き戻し」ではなく、現在のファイルシステムの状態を確認した上での「補償トランザクション」として実装する。

### **目標**
- 「間違えて移動した」等の操作ミスを最小限の手間で復旧
- ファイルシステムの外部変化を検知し、安全に中断またはユーザーへ確認
- Jobシステムを活用した非同期・堅牢な実行

---

## 2. アーキテクチャ

### **ジョブベースの補償操作**
- 成功した Job (Move, Rename, Mkdir, Trash) に対し、対応する `InverseJobSpec` を生成する。
- 例: `Move(A -> B)` の成功に対し、`Move(B -> A)` を生成。

### **トランザクション・ジャーナル**
- 成功した直近 N 件（例: 20件）の操作履歴をメモリ上のスタックで保持。
- アプリ終了時にクリアされる（セッションを跨ぐ Undo は当面対象外）。

---

## 3. ロールバック実行フロー

1. **トリガー**: ユーザーが `u` (Undo) を押下。
2. **フィンガープリント検証（Pre-flight Check）**:
   - 元の操作先（現在の Undo 元）にファイルが実在するか確認。
   - サイズ、更新日時、属性をチェックし、操作直後から変化がないか検証。
3. **実行判定**:
   - **整合性OK**: 自動的に逆 Job を発行。
   - **整合性NG (競合)**: 競合ダイアログを表示（後述）。
4. **完了通知**: 実行結果をタスクパネルへ出力。

---

## 4. 競合解決ダイアログ

外部プロセスや別アプリによってファイルが変更・削除・移動されていた場合、以下の選択肢を提示する：

- **強制実行 (Force)**: メタデータの差異を無視して取り消しを試行。
- **スキップ (Skip)**: そのファイルの取り消しを中止。
- **個別確認**: 複数ファイルの場合、1件ずつ状況を表示してユーザーに判断を仰ぐ。

---

## 5. 制限事項

- **Delete (物理削除)**: ゴミ箱（Phase 7.7）を経由しない物理削除は、データが失われているため Undo 不可。
- **内容の復元**: ファイルの「移動」や「名前変更」は復元するが、ファイル「内容」の変更（上書き等）の Undo は対象外。
- **外部依存**: ロールバック先が別のファイルで埋まっていた場合（衝突）、既存の衝突解決ロジックへ委譲する。

## 8. 実装順の決定（2026-07-28）

**あ）「Undo 対象表の操作を先に実装してから 7.6 に着手」を採用。** 根拠 3 点:

1. **レコードスキーマの手戻りが最大リスク**。Operation Report と Undo ジャーナルは同一の
   per-file 結果レコードを共有する。現存する Copy/Move/Rename/Mkdir（Source→Destination 型）
   だけでスキーマを固めると、in-place 型（属性・タイムスタンプ変更 = 旧値保持が必要）、
   Trash 削除（ゴミ箱内位置との対応）、Create Link（リンク先情報）が収まらず作り直しになる。
   全操作の「形」が出揃ってからレコードを設計する方が安全。
2. **Delete Undo は 7.7（Trash）が前提**。「Delete (Trash) ○」は 7.7 実装後にしか成立しない。
   現在の Delete は完全削除であり Undo 不能。
3. い）Undo 先行の唯一の利点「後続操作が最初から契約に沿って書ける」は、既存 4 操作が
   どのみち fail-fast からの改修必須である以上、優位性が薄い。

**今すぐ資産化するガイドライン**: 今後の新操作 executor は fail-fast ではなく per-file に
ループして結果を積む構造（`Vec<(source, dest, outcome)>` 相当）で書くこと。
これだけ守れば Operation Report 導入時の改修が機械的になる。

**残る未決事項（2026-07-30 更新）**: 前提操作は 7.7 Trash・7.11 属性/タイムスタンプ変更・
7.12 Create Link/Create File の3つに確定。**7.11・7.12 は実装完了**（[7.6.attribute_timestamp_edit.md](7.6.attribute_timestamp_edit.md)・
[7.6.create_link_file.md](7.6.create_link_file.md) 参照、実装順は Create File→属性変更→
タイムスタンプ変更→Create Linkで実施）。残るは 7.7 Trash のみ。7.6 本体（Undo/Redo）着手は
7.7 完了後。
