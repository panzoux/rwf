# Phase 7.12 — Create Link / Create File

**作成日**: 2026-07-29
**状態**: 実装完了（2026-07-30。設計どおりに実装、全テストグリーン。Junction作成の`mklink /J`シェルアウトは
`/D`でAutoRun無効化が必要と判明— 実装時にClink等のシェル拡張がexit codeを汚染する事象を発見・対処）
**対象**: シンボリックリンク/ハードリンク/（Windows）ジャンクション作成、および空ファイル作成。
[7.6 Undo/Redo](7.6.transactional_rollback.md) の前提操作。

---

## 1. 背景・位置づけ

7.6（Undo/Redo、Operation Report）は Undo対象表（[7.6.operation_report_ui.md](7.6.operation_report_ui.md)）で
Create Link / Create File を `○` として要求しているが、現状 `JobKind` は一切実装されていない。
`FilesystemBackend` にはリンク作成・空ファイル作成のメソッドが存在せず、リンクは読み取り（検出・表示）
側のみ実装済み（`LinkKind` enum、`symlink_metadata` による検出、File Information ダイアログでの
表示）。

参照実装（TWF, `specs/twf/`）の `CreateNewFileDialog` はファイル名テキストフィールドのみで、
Create Link に相当する機能はTWFに存在しない。本機能は rwf 独自のUXとして設計する。

---

## 2. Create File の位置づけ（再検討済み）

空ファイル作成は `type nul>$I"new file"` のようなカスタムコマンド + マクロ置換（`$I` 等、
[CLAUDE.md](../CLAUDE.md) 記載の単文字マクロ）で既に代替可能であり、「タイプするより楽」程度のUX差
では内蔵機能化する理由として弱い。

**それでも内蔵Jobとして残すべき理由**は「速さ」ではなく「Undo/Operation Report追跡対象になれるか」:

- マクロ経由の `cmd /C type nul>...` はRWFのJobシステム上は汎用外部コマンド実行としてしか記録されず、
  Create File固有の意味（何を作ったか、Undo=削除）を持てない。Undo対象表がCreate Fileを `○` と
  明記している以上、ネイティブな `CreateFile` Job型を持たない限り7.6のUndoから漏れる。
- 副次的利点: Mkdir同様にディレクトリ再読み込み+カーソル移動が自動で起きる、cmd.exeへのシェルアウト
  （ウィンドウのちらつき・環境依存）が不要、エラーが既存のJobエラーダイアログに統一される。
- 実装コストはMkdirとほぼ同一（空ディレクトリ作成→空ファイル作成に変えるだけ）で、費用対効果は良い。

**結論**: 内蔵ダイアログとして残すが、スコープは最小限に留める。サイズ指定などの拡張は追加しない
（あらかじめサイズ指定してファイルを作る需要はファイラーの主要ユースケースではなく、必要なら既存の
カスタムコマンド機構で十分）。TWFの `CreateNewFileDialog` と同等、ファイル名1フィールドのみ。

## 3. ダイアログ設計

### ダイアログ分割: Create File と Create Link は別ダイアログ

単純操作（ファイル名入力のみ）にモード切替の認知負荷を持ち込まない。`CreateFileDialog` は
既存の汎用 `Input` ダイアログ（`CreateDirectory`/Mkdirが使っているものと同型、
`rwf-bin/src/ui/dialog/basic.rs` の `DialogContent::Input` 分岐）をそのまま流用する。
prompt行「File name:」+ textbox行 + hint行の3行のみで、作成先ディレクトリの表示行は**持たない**
（`CreateDirectory` ダイアログが場所を表示していないのと同じ扱い。作成先は常に現在ペインの
カレントディレクトリで固定・非表示）。

### 起動キー

- Create File: **`N`**（[default_keybindings.json](../rwf-lib/resources/default_keybindings.json)
  未使用。`K`=CreateDirectoryと同系統の「大文字1文字=作成系コマンド」に揃える）。
- Create Link: **`;`**（2026-07-30 変更。当初 `Ctrl+l` を予定していたが実機で使用不可と判明
  — 多くのターミナルが Ctrl+L を「画面クリア」等に予約しておりアプリまで届かない。
  代替候補の `Shift+;` も不採用: このコードベースの `format_key_event`（`rwf-lib/src/input/mod.rs`）
  は記号キーに対して常に「シフト後の文字そのもの」でキー文字列を作る仕様で、`Shift+<記号>` という
  表記のバインドは構造的に一致し得ない（Ctrl+L と同じ「サイレントに発火しない」クラスの不具合になる）。
  `:` は既に `FileMaskFilter` に割当済みのため、未使用の `;`（無シフト）を採用）。

### Create Link ダイアログ

```rust
pub struct CreateLinkDialog {
    pub link_name: String,     // 自由入力可。既定値=targetのファイル名
    pub target: Location,      // 非入力・表示専用。ダイアログを開いた時点のカーソル位置アイテムに固定
                                // （複数マーク時は先頭1件）。Enter中の変更は不可 — 別対象にリンクしたい
                                // 場合はダイアログを閉じてカーソルを合わせ直す
    pub dest_dir: PathBuf,     // 非入力・表示専用。常に state.opposite_pane().current_location
    pub kind: LinkCreateKind,  // Symlink/Hardlink/(Windows)Junction、Tabで循環
    pub ui: DialogUiState,
}
pub enum LinkCreateKind { Symlink, Hardlink, #[cfg(windows)] Junction }
```

**target を選択アイテム固定・非入力にする**（2026-07-29 決定）。当初は自由編集可能なテキスト
フィールドとして設計していたが、以下の理由で単純化した:
- target が動く前提だと、入力のたびにType選択の妥当性を再判定し、既に選んでいたType
  （例: Junction）が急に無効化されるといった「Type選択状態との矛盾」が起こり得る。target を
  固定すれば、Type制約はダイアログを開いた時点で一度だけ計算すればよく、矛盾が原理的に発生しない。
- 「選択中のファイルにリンクを作る」が実際のユースケースのほぼ全てであり、任意パスへの手入力は
  むしろ稀。単純さを優先する。

**レイアウト**（上から）: Type選択行（+選択肢ごとの制約理由行、target固定時に1回だけ計算） →
空行 → 「Link name:」ラベル → `dest_dir`表示行（非編集） → `link_name`編集行 → 空行 →
「Target (what it points to):」ラベル → `target`表示行（非編集） → OK/Cancelボタン。
編集可能なのは `link_name` のみ（フォーカス循環は Type行 → link_nameテキストボックス → OK → Cancel）。

- **dest_dir は非入力・対向ペイン固定**。`state.opposite_pane().current_location`
  （`state/mod.rs:383`）を常に使用し、切り替えキーは持たない（同一ペインへの作成はほぼ使われない
  ため既定を「今いない方のペイン」に固定し、選択の手間自体を無くす。専用ピッカーダイアログは作らない）。
- **target はダイアログを開いた時点のカーソル位置アイテムに固定**（複数マーク時は先頭1件を採用。
  Create Link自体は v1 では1リンク=1操作。バッチリンク作成は非対応、必要になれば別途設計）。
  選択中アイテムは既にパネル一覧から取得済みの実在エントリのため、存在確認は不要。
- **target のディレクトリ判定・同一ボリューム判定はダイアログを開いた時点で一度だけ計算**し、
  Type選択の制約に使う:
  - ディレクトリかファイルか。Junction は Windows かつ「ディレクトリ」の場合のみ選択可（グレーアウト
    + 理由表示）。
  - `dest_dir` と同一ボリューム（ドライブ）かどうか。Hardlink は同一ボリュームの場合のみ選択可
    （グレーアウト + 理由表示）。Symlink・Junction はボリューム制約なし。
  - 上記はUI側の事前絞り込み（誤操作防止のヒント表示）であり、最終判定はバックエンドの `Result`
    から Job エラーとして表面化させる（事前判定の見落としを実行時エラーで確実に捕捉する二段構え）。
- SymlinkはWindowsで権限不足になりうる旨を1行ヒント表示するに留め、事前権限チェックはしない
  （`ERROR_PRIVILEGE_NOT_HELD` はJob失敗として通常のエラーダイアログに出す）。
- 解決後の `dest_dir/link_name` に既にファイルが存在する場合 → 新規UIを作らず、既存の
  `file_conflict.rs` の衝突解決フローに乗せる（copy/move時と同じ体験）。`dest_dir` 自体の存在確認は
  不要（対向ペインは常に実在するディレクトリを開いているため）。

## 4. データモデル・Job

```rust
CreateLink { target: Location, link_path: Location, kind: LinkCreateKind },
CreateFile { location: Location },
```

`FilesystemBackend` トレイトに `create_link`/`create_file` を追加、`local.rs` にのみ実装
（`Location::Local` 以外はbail）。

- Symlink: `std::os::windows::fs::symlink_file/symlink_dir` / `std::os::unix::fs::symlink`
- Hardlink: `std::fs::hard_link`
- Junction: 手書きのreparse point操作ではなく、
  `std::process::Command::new("cmd").args(["/C","mklink","/J",...])` でのシェルアウトを推奨
  （コードベースが外部コマンド実行を既に持つ方式に合わせる）

`job_executor.rs` に `execute_create_link`/`execute_create_file` を追加。Mkdir/Rename/Deleteと
同じdispatchパターンに従う。

**ダイアログ側のType制約判定用ヘルパ**（Job実行とは別に、ダイアログを開いた時点で一度だけ呼ぶ
軽量チェック。target は固定のため再計算は不要）:
- ディレクトリ判定: `std::fs::symlink_metadata` の結果を流用（`local.rs` の既存シンボリック
  リンク検出ロジックと同じ手段。target は選択中アイテム由来なので存在確認は不要）。
- 同一ボリューム判定: Windows は `target_path`/`dest_dir` のドライブ文字（`C:`等）またはUNC先頭を
  比較する簡易実装で十分。Unix は `std::os::unix::fs::MetadataExt::dev()` の一致で判定
  （`#[cfg(unix)]`）。いずれも `backend.rs` に新規メソッドを増やさず、ダイアログ層のヘルパ関数
  （新規 `rwf-lib/src/model/dialog/create_link.rs` 内 or 共有ユーティリティ）で完結させる。

## 6. 実装順序

推奨実装順（リスクが低い順に積み上げる。[7.6.attribute_timestamp_edit.md](7.6.attribute_timestamp_edit.md)
とあわせた全体順序）:

1. **Create File** — 最小サイズ、プラットフォーム分岐なし、Mkdirとほぼ同型。「対象ごとにVecへ結果
   蓄積」パターンを安価に検証できる。
2. 属性変更（[7.6.attribute_timestamp_edit.md](7.6.attribute_timestamp_edit.md) 参照）
3. タイムスタンプ変更（同上）
4. **Create Link** — プラットフォームリスクが最も高い（権限チェック、junctionのシェルアウト、
   hardlinkの同一ボリューム検証）。1〜3で確立したパターンの上に乗せる。

## 8. 未解決・今後の課題

- Create Linkのバッチ（複数リンク一括作成）は今回スコープ外、要望が出れば別途設計
- CLIとの比較でのUX価値: パス選択をペイン閲覧経由にできる点（`ln -s`/`mklink` のようなフルパス
  入力・エスケープが不要）、リンク種別をプラットフォーム/対象に応じて制約できる点（Windowsで
  ディレクトリ以外にJunctionを選ばせない等）が主な差別化。Create File自体の単体UX差は小さく、
  正当化根拠は主に §2 のUndo/Operation Report追跡にある。
