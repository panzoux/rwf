# Undo / Operation Report UI 設計仕様

**作成日**: 2026-07-28
**状態**: UI/UX 仕様の正（Phase 7.6 の設計改訂版。力学・実装詳細は [7.6.transactional_rollback.md](7.6.transactional_rollback.md)）

## 概要

本ファイラーでは、一般的な「Undo履歴」を持つのではなく、**各ファイル操作(Operation)ごとに生成される Operation Report（操作レポート）** を中心として設計する。

Undo/Redoは独立した履歴機能ではなく、このOperation Reportに付随する機能として扱う。

これにより、

* 実行結果確認
* エラー確認
* Undo可否確認
* Undo対象選択
* Undo実行
* Redo実行

をすべて同一UIで実現する。

---

# 基本方針

## Undoは「逆操作」ではない

Undoとは単純な逆操作ではなく、

1. 現在状態を検証
2. 実行可能なものを判定
3. ユーザーへ通知
4. Undo実行

という流れとする。

ファイルシステムは外部アプリや他ユーザーによって変化するため、「以前の状態へ戻す」ことは保証できない。

そのため、Undoは常に現在状態を確認した上で実行する。

---

## Operation Report中心

各Copy / Move / Rename / Deleteなどの操作終了時にOperation Reportを生成する。

Operation Reportには

* 成功
* 失敗
* 詳細理由
* Undo可否

が保存される。

UndoはOperation Reportから実行する。

---

# Undo対象

| Operation          | Undo |
| ------------------ | ---- |
| Copy               | ○    |
| Move               | ○    |
| Rename             | ○    |
| Create File        | ○    |
| Create Directory   | ○    |
| Delete (Trash)     | ○    |
| Delete (Permanent) | ×    |
| Attribute Change   | ○    |
| Timestamp Change   | ○    |
| Create Link        | ○    |
| Create Archive     | ○    |
| Extract Archive    | ×    |

> 注（2026-07-28 現状）: Create File / Delete (Trash) / Attribute Change / Timestamp Change /
> Create Link は JobKind 自体が未実装。7.6 着手前にこれらの操作を固める方針
> （実装順の決定は [7.6.transactional_rollback.md](7.6.transactional_rollback.md) 参照）。

## 完全削除

完全削除は不可逆操作とする。

Undo対象外。

理由

* 操作の意味と矛盾する
* 一時バックアップ等を持つと仕様が複雑になる

---

## 展開(Extract)

Undo対象外。

理由

展開結果は通常削除するだけで戻せるため。

Undo専用機能を設けるメリットが小さい。

---

# Undo情報

Undoには以下を保持する。

* Source
* Destination
* File ID / inode
* サイズ
* 更新日時
* 必要ならHash

目的は

* 同一ファイル判定
* 変更検知
* Undo可否判定

である。

---

# Undoフロー

```
Undo開始

↓

事前検証

↓

問題があれば通知

↓

Undo実行

↓

結果表示
```

---

# 事前検証

Undo開始時点で判定可能な問題を確認する。

例

* 戻し先が存在
* ファイル変更済み
* 対象消失
* 親ディレクトリ不存在

---

## 重要

途中失敗は2種類ある。

### ① Undo開始前に分かるもの

例

* 戻し先が既に存在
* ファイル変更済み

これは事前検証で検出する。

ユーザーへ

「○件戻せます」
「△件戻せません」

を通知する。

例

```
Undo Move

戻せる : 117

戻せない : 3

理由

Modified : 1

Already Exists : 2

[Continue]

[Cancel]
```

ユーザーは理解した上で実行できる。

---

### ② 実行中に発生するもの

例

* 他アプリが開いた
* 権限変更
* ネットワーク切断
* ディスク切断

これは事前検証では防げない。

Undo終了後、

成功件数

失敗件数

理由

を表示する。

---

# Operation Report

Operation ReportはJobとは別概念である。

Job

* 実行中管理
* Progress
* Scheduler

Operation Report

* 実行結果
* Undo
* Redo
* エラー確認

責務を分離する。

短い表現を使用する。

例

Fail

一覧性を重視する。

---

# Undo列

Undoableではなく

Undo

とする。

セル内容

```
✓

×

-
```

意味

✓

Undo可能

×

Undo対象だが現在不可

*

Undo対象外または操作失敗

詳細理由は下部ペインで表示する。

長い文字列は一覧へ表示しない。

# Undo Report

Undoを実行すると、

Undo Operation Report

が生成される。

例

```
Undo Copy Report
```

この場合、

最後の列はRedoへ変わる。

```
Source

Destination

Result

Redo
```

Redoも同じUIで扱える。

例

```

```

これにより

Undo Selected

が可能になる。

全件ではなく必要なものだけ戻せる。

# Reportの保持

Operation Reportは複数保持する。

Copy

Move

Rename

Delete

Undo

など、それぞれの実行ごとにReportを生成する。

保持数は無制限ではなく、比較的少数（例: 10件程度）を想定する。

理由

大量保持すると

* 操作対象を見失う
* 誤Undo
* 誤Redo

など事故が増えるため。

古いものは閲覧のみとし、Undo操作対象から外す設計も検討対象とする。

保持件数・保持ポリシーは設定可能としてもよい。

# UI遷移

```
Copy

↓

Operation Report

↓

Undo

↓

Undo Report

↓

Redo
```

Undo専用画面は存在しない。

> 注（2026-07-28 決定）: Operation Report は**常に手動（キー）で開く**。
> 操作完了時の自動表示は行わない（連続操作の邪魔になるため）。
> 遷移図の `Copy → Operation Report` は「Report を開けば直前の Copy の結果が見える」の意。

---

# Jobとの関係

Job

↓

Completed

↓

Operation Report生成

↓

Undo

↓

Undo Job

↓

Undo Report生成

つまり

Undoも通常JobとしてSchedulerへ投入される。

Operation Reportは実行後の結果を保持するだけである。

# 設計思想・議論の経緯

当初は一般的な「Undo履歴」を想定していた。

しかし検討を進める中で、

ユーザーが本当に見たいものは

* 何を実行したか
* 成功したか
* 失敗したか
* なぜ失敗したか
* Undoできるか

であることが分かった。

つまり中心になるべきなのはUndoではなく、「操作結果」である。

そこで、

Operation Report

という概念へ整理した。

この変更により、

* 実行結果確認
* エラー確認
* Undo
* Redo

を同じ画面・同じテーブルで扱えるようになった。

さらにTUIとの相性も良く、

「一覧＋詳細ペイン」

という定番レイアウトを採用できる。

また、当初は「Action」列（Undo/Retry/Resolve等）も検討したが却下した。

理由は、

Actionという抽象概念は学習コストが高く、

ユーザーが

「結局どうすればいいの？」

と迷いやすいためである。

代わりに

Result

Undo

（Undo ReportではRedo）

という具体的で意味が明確な列を採用する。

これは

「誰でも見たら理解できる」

ことを最優先した判断である。

また、長い状態名（Available / Unavailable等）は一覧性を損なうため採用せず、

✓

×

*

など短い記号を用い、

詳細理由は下部ペインで確認する。

この設計は、

**一覧は一覧らしく、詳細は詳細らしく**

というTUI設計の原則にも一致する。

最終的に、

Undo機能を設計していたつもりが、

「Operation Report」という実行結果UIを設計する方向へ自然に発展した。

このOperation Reportが、実行後の確認・分析・Undo・Redoの中心UIとなる。
