# 7.25 ペイン幅の変更（Ctrl+Left / Ctrl+Right）

**状態**: `[ ]` 未着手（2026-09-18 起票、同日 仕様決定を反映）
**由来**: Future candidates「動的ペイン幅調整」（旧 Phase 8.3）のうち**キー操作分**を前倒し。マウスは対象外。

## 1. 目的

左右ペインの境界を `Ctrl+Left` / `Ctrl+Right` で動かし、「ファイル名があと 1〜2 文字見えれば足りる」場面で
片側を少しだけ広げられるようにする。縦方向の `Ctrl+Up` / `Ctrl+Down`（タスクパネル高さ）と対になる操作。

## 3. 仕様

### 3.1 操作

| キー | 動作 |
|------|------|
| `Ctrl+Right` | 境界を右へ **2 列**（左側が広がる） |
| `Ctrl+Left` | 境界を左へ **2 列**（右側が広がる） |
| `Ctrl+\|`（Unix 端末では `Ctrl+4` として届く） | 均等分割に戻す |

- 方向はアクティブペインに依存しない（矢印の向き＝境界の移動方向）。`Ctrl+Up` でタスクパネル境界が上へ動くのと同じ規則。
- アクション名: `WidenLeftPane` / `WidenRightPane` / `ResetPaneSplit`。
- タブ切替の `Ctrl+Left/Right` は**廃止**し、`Ctrl+PageUp/PageDown` と `Alt+h/l` を残す。

### 3.2 値: 左ペインの幅（列数）と、その幅を決めたときの端末幅

状態は **`left_pane_width: Option<PaneSplit>`**、`PaneSplit { left: u16, at_total: u16 }`。未使用の `pane_split_ratio: f64` を置き換える。

- **`None` = 均等分割**（起動時・リセット後）。描画は現在と 1 列も変わらない。
  奇数幅で現行 `Percentage(50)` がどちらに 1 列寄せるかは T3 で実測し、`None` の左幅をそれに合わせる。
- **表示する左幅は描画時に計算する**: `round(left × 現在の端末幅 / at_total)`、そのあと各側**最小 16 列**でクランプ。
  右幅は `端末幅 − 左幅`。32 列未満（両側 16 を満たせない）は均等。
- **リサイズしても保存値は書き換えない**。毎回丸めた値を保存すると、端末の端をドラッグしたときの大量のリサイズイベントで
  丸め誤差が積み重なり、比率がずれていくため。元の値から毎回計算すれば、元の幅に戻したとき元の列数に戻る。
  狭めたときのクランプも表示だけに効くので、また広げれば元の比率に戻る。
- **キー操作は「今表示されている左幅」を起点にする**: 表示幅 ± 2 をクランプし、`PaneSplit { left: その値, at_total: 現在の端末幅 }` で保存し直す。
  `None` からは均等時の左幅が起点。クランプで表示が変わらなければ何もしない（UI 変化なし）。
  表示幅を起点にするので、狭い端末で押しても見た目が動かないまま値だけ変わることはない。

具体例:

| 操作 | 保存値 `(left, at_total)` | 端末幅 | 左 / 右 |
|------|--------------------------|-------:|---------|
| 起動時 | `None` | 120 | 60 / 60 |
| `Ctrl+Right` ×2 | (64, 120) | 120 | 64 / 56 |
| 端末を 160 列へ拡大 | 変わらず | 160 | 85 / 75（64×160/120=85.3） |
| 120 列へ戻す | 変わらず | 120 | 64 / 56（元どおり） |
| 端末を 34 列へ縮小 | 変わらず | 34 | 18 / 16（18.1→18） |
| 33 列へ縮小 | 変わらず | 33 | 17 / 16（17.6→18 を右 16 確保でクランプ） |
| 160 列で `Ctrl+Right` | (87, 160) | 160 | 87 / 73 |
| `Ctrl+Right` を押し続ける（160 列） | (144, 160) で止まる | 160 | 144 / 16 |
| `Ctrl+\|` | `None` | — | 均等 |

### 3.3 スコープ

- **全タブ共通**（`LayoutState` に置く。タスクパネル高さと同じ扱い）。
- **SideBySide ビューアも同じ境界を使う**。ファイルペインが左でビューアが右なら、`Ctrl+Right` でファイルペイン側が広がりビューアが狭まる。
  ビューアにフォーカスがあるときのキーは `textViewerBindings` 側で解決されるので、境界を動かすのはファイルペインにフォーカスがあるときのみ。
- **永続化**: `SessionState.left_pane_width: Option<PaneSplit>`（`#[serde(default)]` = `None`）。起動時の端末幅が保存時と違っても比率で表示される。
  セッション JSON は config ではないので PascalCase 規則の対象外（既存 `task_panel_height` と同じ snake_case）。
- **対象外**: マウスでのドラッグ、config.json での初期値指定、上下分割。

### 3.4 ビューアの検索ジャンプ幅（本件で一緒に直す）

**今の動き**（コードから導いたもの。T0 のテストで再現してから直す）

`/` 検索でヒットした行が長いとき、`jump_to_match` は「ヒット末尾が `content_width` 内なら横スクロール 0、はみ出すならヒットが右端に来るよう
`column_offset` を動かす」。この `content_width` が端末全幅 − 10 固定。1000 行未満のファイルの行番号プレフィックス `" NNN | "` は 6 列、枠は左右 2 列。

| 端末 120 列 | 実際に見える本文幅 | `content_width` | ヒットが 80〜85 バイト目 |
|-------------|-------------------:|----------------:|---------------------------|
| FullScreen | 120 − 2 − 6 = **112** | 110 | 85 ≤ 110 → offset 0。見える（差 2 列は実害ほぼ無し） |
| SideBySide 均等（ビューア 60 列） | 60 − 2 − 6 = **52** | 110 | 85 ≤ 110 → offset 0。**0〜51 列しか見えず、ヒットが画面外** |
| SideBySide でビューア側を 46 列に狭めた後 | 46 − 2 − 6 = **38** | 110 | 同上。狭めるほど画面外になる範囲が広がる |

つまり SideBySide では今も、表示幅を超えた位置のヒットへジャンプしても横スクロールしない。本件でビューア幅を可変にすると、この差がさらに大きくなる。

**直した後**

- 実際の本文幅を、描画と**同じ純関数**で rwf-lib 側でも計算する:
  `ビューア枠の幅（FullScreen なら端末幅、SideBySide なら §3.2 の分割のビューア側）− 2 − 行番号プレフィックス（3/4/5 桁 → 6/7/8 列）`。
- **検索ジャンプの時点で計算して `jump_to_match(cw)` に渡す**（遅延計算）。リサイズや境界移動のたびに先回りして書き込む
  `content_width` フィールドと、`UpdatePaneWidth` 内のその更新は削除する。
- 同じ例で: SideBySide 均等 → 本文幅 52、ヒット 80〜85 → `column_offset = 85 − 52 = 33` → 33〜84 列が見え、ヒットは右端。
  ビューア 46 列 → 本文幅 38 → `column_offset = 47` → 47〜84 列、ヒットは右端。FullScreen → 本文幅 112 → offset 0（現状どおり）。
- 既知の別件（本件では直さない）: `jump_to_match` はバイト位置で比較するため、CJK を含む行では表示列とずれる。
