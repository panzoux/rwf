# Phase 7.15 — Diagnostic Report (診断レポート機能)

**Created**: 2026-08-11
**Status**: Design Document
**Priority**: Phase 7 — run in parallel with 7.6, land on `main` first

---

## Executive Summary

An explicitly started/stopped **diagnostic session** that captures a reproducible bug case
as a single self-contained folder: structured events, logs, TUI screen snapshots, environment
metadata, and a user-written problem description.

The goal is not log storage. It is making this chain reconstructible after the fact:

```
user input → state change → job/event → UI render → problem
```

**Deliverable**: `F12` starts/stops a session, `F11` takes a screen snapshot at any time,
the session end prompts for a description, and everything lands in
`<data_dir>/rwf/diagnostics/<timestamp>/` in a format an AI or script can read directly.

**Target problem classes**: transient UI stalls, delayed job-completion reflection, async
tab creation, state/display mismatch, keys that appear to do nothing, non-deterministic
repros, and platform-specific (Windows/Linux/network drive) behaviour.

---

## 1. Codebase Reality Check

> This section records what was verified in the source on 2026-08-11. The original feature
> proposal assumed an event architecture that does not exist; the real one is **simpler and
> better suited** to this feature. Read this before writing code.

### 1.1 `AppEvent` is dead code — do not build on it

`rwf-lib/src/app_event.rs` declares:

```rust
pub enum AppEvent {
    Input(crossterm::event::KeyEvent),
    Job(crate::worker_pool::JobEvent),
}
```

`rwf-lib/src/lib.rs:20` declares the module. **There are zero other references in the
workspace** — the enum is never constructed and never matched. There is no `AppEvent` bus,
no `AppEvent` dispatch, and no "main event processing" stage that consumes it.

Any design that routes diagnostics through `AppEvent` is building on nothing.

**Side task**: this dead module should be deleted, but that is a separate cleanup — not part
of 7.15. Do not "revive" it to serve diagnostics.

### 1.2 The real choke points

| Concern | Actual location | Note |
|---|---|---|
| **All state transitions** | `update_state()` — `rwf-lib/src/state/mod.rs:1044` | single free function; `Transition` derives `Debug` |
| **All job events** | `process_pending_events()` — `rwf-lib/src/event_receiver.rs:78` | maps `JobEvent` → `Transition` → `update_state()` |
| **Raw key input** | `App::handle_events()` — `rwf-bin/src/app.rs:615` | polls crossterm directly with a timeout |
| **Render + screen contents** | `App::render()` — `rwf-bin/src/app.rs:1947` | main-loop owned |
| **Job submission** | `App::run()` pending-job block — `rwf-bin/src/app.rs:358-462` | `pool.submit_job(...)` call sites |
| **Logs** | `rwf-lib/src/logging.rs:151` | `tracing_subscriber::registry()` + one file layer |

**Key consequence**: because `process_pending_events` funnels `JobEvent` through
`map_job_event_to_transition` into `update_state`, **observing `update_state` alone captures
both state transitions and job events**. Total instrumentation is **3 call sites plus one
tracing layer** — the "don't scatter `record()` everywhere" principle is achievable almost
for free.

### 1.3 Snapshots are nearly free, and precedent exists

After `terminal.draw(...)`, ratatui's back buffer *is* the rendered screen.
`render_dialog_to_string()` (`rwf-bin/src/ui/dialog/snapshot_tests/mod.rs:66`) already does:

```rust
format!("{:?}", terminal.backend().buffer())
```

Because `App::render()` runs on the main loop, the "snapshot must not reach into UI state
from another thread" requirement is satisfied **by construction**. No ownership design work
is needed — only a `snapshot_requested` flag checked after `draw()`.

Note `{:?}` on `Buffer` emits a debug dump including style runs — verbose and awkward to
read. See §5.3 for the plain-text extraction this feature actually wants.

### 1.4 Logging can be teed with zero call-site changes

`init_logging()` builds a `tracing_subscriber::registry()` with a single file layer writing
`session.log` (text format, `LocalTime::rfc_3339`, rotating at 10 MB). Adding a **second
`Layer`** that forwards to the diagnostic collector gives `logs.jsonl` without touching a
single `tracing::info!` call site.

**Constraint**: `init_logging` calls `.init()` exactly once at startup with a fixed layer
set. The diagnostic layer must therefore be installed **unconditionally at startup** and gate
itself internally on the session-active flag.

### 1.5 The motivating bug already has a suspect

The proposal cites "New Tab 後に約1秒 UI 反映が遅れる". The main loop's adaptive sleep
(`rwf-bin/src/app.rs:539`) starts from:

```rust
let mut next_wakeup = Duration::from_secs(1); // Default safety poll
```

A ~1 s delay is exactly the signature of a job completion that failed to shorten that
wakeup. This is a hypothesis, not a conclusion — but it means the `Wake` event (§4.2) that
records the computed `next_wakeup` is the single highest-value event in this feature.

### 1.6 Input is not async

`handle_events()` polls crossterm synchronously with a timeout. There is no tokio channel
carrying input. Any design assuming an async input stream is wrong.

## 2. Design Principles

1. Diagnostics is an **observer**, never part of the control path.
2. No blocking I/O on the UI loop or in job workers.
3. Never violate main-loop ownership of UI/render state.
4. Reuse existing `Transition` / `JobEvent` / render boundaries; do not invent new ones.
5. No scattered `record()` calls — 3 sites plus a tracing layer.
6. Correlate everything by **sequence number + timestamp**.
7. One session = one directory.
8. Snapshots: on demand, plus automatic at start and end.
9. Available in **release** builds, not debug-only.
10. A diagnostics failure must never take down rwf.
11. Output format optimised for machine reconstruction of the timeline.

---

## 3. Architecture

```
 Input ──┐
 Job ────┤   (3 observation points + 1 tracing layer)
 State ──┤
 Render ─┘
         │  DiagnosticHandle::observe()   ← lock-free, one atomic load when disabled
         ▼
   tokio::sync::mpsc::UnboundedSender<DiagnosticRecord>
         │
         ▼
   DiagnosticWriter  (dedicated std::thread, blocking_recv)
         │
         ▼
   diagnostics/<session>/{metadata.json, events.jsonl, logs.jsonl, snapshots/, report.txt}
```

### 3.1 Global handle, not a field on `AppState`

`update_state()` is a free function in `rwf-lib`; the tracing layer lives outside any app
struct; job workers run on other threads. Threading a collector reference through all of
these means signature churn across the whole codebase.

**Decision**: a process-global handle, mirroring how `tracing` itself works.

```rust
// rwf-lib/src/diagnostics/mod.rs
static HANDLE: OnceLock<DiagnosticHandle> = OnceLock::new();

pub struct DiagnosticHandle {
    active: AtomicBool,
    seq:    AtomicU64,
    tx:     mpsc::UnboundedSender<DiagnosticRecord>,
}
```

This also **structurally enforces principle 1**: the collector has no access to `AppState`,
so it cannot become part of the control path even by accident.

`tokio::sync::mpsc::UnboundedSender` is chosen because it is `Sync` (so it can live in a
`static`), `send()` is synchronous and lock-free (safe to call from the UI loop), and tokio
is already a workspace dependency. `std::sync::mpsc::Sender` is `!Sync` and would require a
`Mutex` — exactly the contention the design is trying to avoid.

### 3.2 Disabled cost

```rust
pub fn observe(f: impl FnOnce() -> DiagnosticRecord) {
    if let Some(h) = HANDLE.get() {
        if h.active.load(Ordering::Relaxed) {
            let _ = h.tx.send(f());   // send failure is ignored by design
        }
    }
}
```

When no session is running: one `OnceLock` read plus one relaxed atomic load. The closure is
**not evaluated**, so payload formatting (`format!("{:?}", transition)`) costs nothing when
inactive. This keeps the feature viable in release builds.

### 3.3 Writer thread

A dedicated `std::thread` (not a tokio task) consuming via `blocking_recv()`:

- File I/O is blocking anyway; a std thread cannot starve the async runtime.
- Creates the session directory lazily on the first record, keeping `mkdir` off the UI loop.
- Appends to `events.jsonl` / `logs.jsonl`; writes snapshot files as they arrive.
- On shutdown: drains the channel, writes `metadata.json` and `report.txt`, flushes, exits.
- **All errors are logged via `tracing::warn!` and swallowed.** A full disk must not stop rwf.

### 3.4 Sequence and time

`seq` is assigned by `fetch_add(1, Relaxed)` inside `observe()` — globally monotonic across
all threads, so ordering survives same-millisecond collisions. Timestamps use
`chrono::Local::now()` (already a dependency, consistent with `logging.rs`).

## 4. Collected Data

### 4.1 Record schema

```jsonc
{"seq": 184, "ts": "2026-08-11T23:41:52.113+09:00", "type": "Key",        "data": {...}}
```

### 4.2 Event types (v1)

| Type | Source | Payload |
|---|---|---|
| `Key` | `handle_events()` | key code, modifiers, resolved action name (**or `null` — a key that mapped to nothing is a first-class finding**) |
| `Transition` | `update_state()` | variant name + truncated `{:?}` of the payload |
| `JobSubmit` | `App::run()` submission block | job id, `JobKind` name |
| `Wake` | end of loop iteration | computed `next_wakeup` ms, `ui_needs_update`, `any_pane_loading` — see §1.5 |
| `Render` | `App::render()` | terminal size, active mode |
| `Snapshot` | `App::render()` | snapshot filename, trigger (`start` / `manual` / `final`) |
| `SessionStart` / `SessionEnd` | lifecycle | — |

`JobEvent` needs no separate type: it arrives as its mapped `Transition`. Record the raw
`JobEvent` variant name inside that `Transition` record where available.

**Deliberately excluded from v1**: per-function call tracing, individual render-widget
events, and unthrottled `JobProgress`.

### 4.3 `Wake` volume guard

When `ui_needs_update` is true the loop sets `next_wakeup = 0` and spins. Recording every
iteration would flood the log. **Record `Wake` only when `next_wakeup > 0`** — i.e. when the
loop is actually about to sleep, which is the informative case and the one that diagnoses
§1.5.

### 4.4 `JobProgress` throttling

`Progress` / `ProgressWithDetail` arrive at high frequency. Throttle to at most one record
per `progress_throttle_ms` (default 500) **per job id**, and always record the first and last
progress value for each job.

### 4.5 Logs

A `tracing_subscriber::Layer` implementation with a field visitor serialising level, target,
file/line, message and fields to `logs.jsonl`. Installed unconditionally in `init_logging`
(§1.4), self-gating on the active flag.

Roles stay separate: `session.log` is the existing human-facing log; `logs.jsonl` is the
machine-readable slice belonging to one diagnostic session.

### 4.6 `metadata.json`

```json
{
  "session_id": "20260811-234152",
  "started_at": "...",
  "ended_at": "...",
  "rwf_version": "...",
  "os": "windows 10.0.19045",
  "arch": "x86_64",
  "terminal": "$TERM / $WT_SESSION if present",
  "terminal_size": [120, 40],
  "config_summary": { "polling_interval_ms": 1000, "loading_poll_interval_ms": 50 }
}
```

`config_summary` carries only timing-relevant fields — **not** the whole config, which
contains user paths, registered folders and custom command lines.

## 5. Snapshots

### 5.1 Capture point

`App` gains `snapshot_request: Option<SnapshotTrigger>`. `App::render()` checks it
immediately after `terminal.draw(...)`, converts the buffer, hands the text to the collector,
and clears the flag. Main-loop ownership is preserved; no other thread touches render state.

### 5.2 Triggers

1. Automatic at session start
2. `F11` at any time, any number of times
3. Automatic at session end (`-final`)

Cap at `max_snapshots_per_session` (default 200) to bound a runaway session; log a warning
once when the cap is hit.

### 5.3 Buffer → text, CJK-safe

**This is the one genuinely tricky piece of the feature.** A wide (CJK) glyph occupies two
cells in the ratatui buffer; the second cell holds an empty symbol as a continuation
placeholder. Naively concatenating `Cell::symbol()` across a row yields correct text only if
empty continuation cells are skipped rather than emitted as spaces — otherwise every CJK
character shifts the rest of the line by one column.

Given that CJK rendering is rwf's headline strength, a snapshot that mangles CJK is worse
than no snapshot. This conversion gets dedicated unit tests (§9) covering ASCII, wide CJK,
and mixed rows.

Output is plain text — one line per terminal row, trailing whitespace trimmed. The `{:?}`
style dump is **not** included in v1 (YAGNI; add later if a colour bug demands it).

## 6. Session Lifecycle

```
F12  → Transition::StartDiagnosticSession
       → install handle, activate, spawn writer thread
       → request start snapshot
       → DIAG indicator appears

 …    user reproduces the problem; F11 snapshots at will

F12  → request final snapshot
       → push report-input dialog (multi-line)
       → on confirm: write report.txt + metadata.json, deactivate, shut down writer
       → on cancel: session still saved, report.txt written with a placeholder line
```

Cancelling the dialog must **not** discard the bundle — the user already did the work of
reproducing the bug.

### 6.1 DIAG indicator

The session must be visibly distinguishable from normal operation to prevent leaving it
running by accident. Render `● DIAG mm:ss` right-aligned on the tab-bar row
(`rwf-bin/src/ui/tab_bar.rs`).

**Open point**: `ui.layout.show_tab_bar` can be `false`. Fall back to the path line in that
case. Decide at implementation; a dedicated full-width bar (LEAP-style) is rejected as it
wastes a row for a purely passive indicator.

Note that an active session forces a redraw every second so the elapsed timer advances —
harmless, but it changes idle-loop behaviour, so it is itself visible in the `Wake` stream.

## 7. Keybindings

`F11` and `F12` are unused anywhere in `default_keybindings.json`.

| Key | Action | Modes |
|---|---|---|
| `F12` | `ToggleDiagnosticSession` | `NormalMode`, `ViewerMode`, `LeapMode` |
| `F11` | `DiagnosticSnapshot` | `NormalMode`, `ViewerMode`, `LeapMode` |

**All three keymaps are required.** Viewer and Leap modes swallow most keys; binding only
`NormalMode` would make it impossible to capture a viewer rendering bug or a Leap filter
stall — a significant fraction of the target problem classes.

## 8. Config, Location, Privacy

### 8.1 Config

PascalCase with `#[serde(default)]` on every field, per the serialization mandate:

```json
"Diagnostics": {
  "Enabled": true,
  "MaxSnapshotsPerSession": 200,
  "ProgressThrottleMs": 500,
  "CaptureLogs": true
}
```

### 8.2 Location

Add `default_diagnostics_dir()` mirroring `default_log_dir()` (`logging.rs:193`): prefer a
local `./diagnostics` when running from a directory that has `./logs`, otherwise
`dirs::data_dir()/rwf/diagnostics`.

### 8.3 Privacy — decided 2026-08-11: **document, do not redact**

A bundle unavoidably contains **every filename and full path the user was browsing**, plus
verbatim screen contents. The feature's purpose is to hand that bundle to an AI, so this is
inherent, not incidental.

**Decision**: write bundles in the clear. The end-of-session dialog states plainly that the
bundle contains file paths and screen contents and should be reviewed before sharing. No
redaction mode in v1.

Rationale: hash-based redaction is substantial work, degrades the AI-readability that
justifies the feature, and — worse — would offer a false assurance of safety while
screenshots still leak paths through rendered text. Honest disclosure beats partial
scrubbing.

Two things this decision still requires:
- `config_summary` in `metadata.json` is an explicit allowlist of timing fields (§4.6), never
  a whole-config dump.
- `diagnostics/` must be added to `.gitignore`.

## 9. Test Strategy

| Layer | Coverage |
|---|---|
| Unit | seq monotonicity under concurrent `observe()`; record JSON round-trip; **buffer→text with ASCII / wide CJK / mixed rows** (§5.3); progress throttling |
| Unit | **disabled collector is a true no-op** — closure not evaluated, nothing sent |
| Integration | start session in a `tempfile` dir → drive transitions → stop → assert directory layout, event ordering, and that `seq` is gap-free |
| Snapshot | DIAG indicator rendering; report-input dialog (both standard sizes, per `snapshot_tests` convention) |
| Regression | the whole existing suite must pass **unchanged** with diagnostics compiled in and inactive |

The last row is the real acceptance criterion: this feature is only correct if it is
invisible when off.

## 10. Implementation Stages

| # | Stage | Content |
|---|---|---|
| 1 | Core | `diagnostics/` module, record types, global handle, writer thread, `events.jsonl`. No UI. |
| 2 | Observation | wire `update_state`, `handle_events`, job submission, `Wake`. |
| 3 | Snapshots | `snapshot_request` flag, CJK-safe buffer→text, `snapshots/`. |
| 4 | Logs | tracing `Layer` → `logs.jsonl`. |
| 5 | Lifecycle & UI | keybindings, transitions, DIAG indicator, report dialog, `metadata.json`, config, `.gitignore`. |
| 6 | Docs | `docs/` entry describing the bundle format for AI consumers. |

Stages 1–2 alone already produce a useful artifact and can be validated against the §1.5
hypothesis before any UI work exists.

## 11. Explicit Non-Goals (v1)

- **Ring buffer for pre-session history** — the original proposal already hedged on this
  ("初期実装で必須とは限らない"). The benefit is real but sizing it requires knowing actual
  event volume, which stage 1–2 will measure. Revisit afterwards.
- Redaction / anonymisation (§8.3).
- Upload or transmission of bundles anywhere.
- An in-app bundle browser or replay viewer.
- Full-fidelity `JobProgress` capture.
- Reviving or extending `AppEvent` (§1.1).

## 12. Relationship to 7.6

7.15 is developed in its own worktree off `main` and merged to `main` **before** 7.6 lands,
so that 7.6 can consume it.

Overlap with the in-flight 7.6 branch (`worktree-phase-7.6-undo-redo`, 4 commits) is small
and additive: 7.6 currently touches `job/job_executor.rs`, `model/operation_report.rs`,
`job.rs`, `model.rs`, `input/file_operations_tests.rs`; 7.15 touches `state/mod.rs`,
`rwf-bin/src/app.rs`, `logging.rs`, plus a new `diagnostics/` module. The only shared files
are ones 7.6 has not modified yet, and the changes are new match arms and new call sites
rather than rewrites.

The motivation for the ordering: transactional rollback across async jobs is exactly the
code that produces "state and display disagree" and "the job completed but the UI never
noticed" bugs — the class 7.15 exists to capture.
