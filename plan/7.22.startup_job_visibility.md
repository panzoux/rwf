# Phase 7.22 — Startup Job Visibility & Failure-Dialog Information Design

**Created**: 2026-09-10
**Status**: **Implemented (2026-09-11)** — all five §4 pieces. See *Implementation notes* at the
end for what was built and where it departs from this design.
**Origin**: diagnostic bundle `20260910-203646`, items (3) and (4). Items (1) and (2) of the
same report are fixed (see `plan/ROADMAP.md` 7.23); these two are what is left.

---

## Executive Summary

Two problems, both about a user being told what is happening:

1. **A directory read is invisible while it runs.** The tab-bar spinner and the task panel
   are both driven by `background_jobs`, and `ReadDirectory` jobs never register there. So a
   tab stuck on an unreachable share shows no spinner, and the task panel says "No active
   tasks" while two jobs are running.
2. **"Operation Failed" is the wrong title and the wrong shape.** On startup the user has
   operated nothing. The dialog should say *what* failed, *where*, *when*, and *why*, and
   offer something to do about it.

## 1. The evidence

From `snapshots/000-start.json` of bundle `20260910-203646`, taken while tab 5 was blocked on
a dead SMB share:

```

5 right loading=True job=JobId(c61fc82f…) \\192.168.11.24\testfol
jobs.active     = [ReadDirectory Running, ReadDirectory Running]
```

and the screen at that same instant:

```
 [1:C:…\diagnostics*|…]  2:D:\|D:\~lc  …  5:\\192.1…\iphone|\\192.…
 …
No active tasks
```

Two jobs running, `is_loading` true on both panes, and **no spinner on tab 5 and no task-panel
entry**, because [`tab_bar.rs:67`](../rwf-bin/src/ui/tab_bar.rs) asks
`state.background_jobs.get_active_job_count(idx)` and the answer is zero.

The user reported this as *"I'm not sure but … the error of tab5 was not shown in the task
pane"*. It is not an intermittent effect: `ReadDirectory` is **never** visible.

## 2. Problem 1 — make pane reads visible

### 2.1 Root cause

`background_jobs` is the "what is rwf doing" surface. Every job that registers there gets a
tab spinner, a task-panel line at start and finish, and a row in the job manager. Registration
happens at a handful of call sites in `rwf-bin/src/app.rs` (delete, trash, copy/move,
extract…). `trigger_initial_directory_reads` and the navigation handlers register with
`state.jobs` only.

The spinner code is already written and correct; it is simply never given anything to show.

### 2.2 The id/index trap — read before implementing

There are **two different tab keys in play**, and they are both `usize`:

| API | meaning |
|---|---|
| `JobSpec::requesting_pane: Option<(usize, ActivePane)>` | tab **id** — matched with `t.id == requesting_tab_id` |
| `JobSpec::with_requesting_pane(tab_idx, …)` | parameter is *named* `tab_idx` but every caller passes an **id**; the name is wrong |
| `BackgroundJobManager::start_job(…, tab_id, …)` | callers pass `state.tabs.active_index` — an **index** |
| `background_jobs.get_active_job_count(idx)` | **index**, as used by `tab_bar.rs` |
| the task-panel log line `[Tab {}]` | `bg_job.tab_id + 1` — an index, printed as a 1-based tab number |

So `background_jobs` is index-keyed and `requesting_pane` is id-keyed. Registering a
`ReadDirectory` naively with its `requesting_pane.0` puts the spinner on **the wrong tab**
whenever a tab has been closed (ids stop matching positions).

**Do one of these deliberately, do not mix them:**

- **(a)** Convert at the registration site: `tabs.iter().position(|t| t.id == tab_id)`. Small,
  local, and leaves the existing ambiguity in place for the next person.
- **(b) Recommended.** Make `background_jobs` id-keyed too, and have `tab_bar.rs` resolve
  index→id. Ids are the only stable key — an index silently means a different tab after a
  close, which is a bug class this repo has already hit (`498c710 fix(tabs): keep the same
  tab active when a tab to its left closes`). Rename `with_requesting_pane`'s parameter to
  `tab_id` in the same change.

### 2.3 What "visible" should mean

Not every directory read deserves a task-panel line — plain navigation would flood it. Suggested
split, cheapest first:

| surface | which reads | why |
|---|---|---|
| **tab spinner** | all of them | already the design; costs nothing; disappears in milliseconds for a local read |
| **task panel** | only reads that are still running after a threshold (~500 ms), plus every failure | a local read finishes before the line would be readable; a slow one is exactly what the user wants to see |
| **job manager** (`Alt+j`) | all of them | it is the complete list by definition |

The threshold matters: without it, every cursor-driven refresh writes two lines and the panel
becomes useless. Reuse `JobManager`'s existing timing rather than adding a timer.

### 2.4 Startup specifically

Ten reads fire at once from `trigger_initial_directory_reads`. The user's own suggestion is
the right shape:

> *like show up tabs and blank panes, show spinners (in the tab) to show what's working now,
> and/or show what's going on in the task pane*

That is already what the code intends — the tabs and blank panes do appear, and the spinner
exists. Registering the jobs is the whole fix for the startup case.

## 3. Problem 2 — the failure dialog

### 3.1 What it says now

After 7.23 the message names the pane, which was the first gap:

```
Tab 5 right pane: Read directory failed: Failed to read directory
\\192.168.11.24\testfol: ネットワーク名が見つかりません。 (os error 67)
```

Still wrong: the **title** is "Operation Failed" when the user operated nothing, the sentence
is a concatenation of three layers' prefixes ("Read directory failed: Failed to read
directory"), there is no hint what to do, and the only button is OK.

### 3.2 Why the title is always "Operation Failed"

`Dialog::from_job_failure_in` classifies by **English substring match** on the error text:

```rust
} else if error_message.to_lowercase().contains("not found") {
    ErrorType::FileNotFound
```

The user's Windows is Japanese, so the message is `ネットワーク名が見つかりません。` and no
arm ever matches. Every failure on a localized Windows falls to the `_ => "Operation Failed"`
default. **This is a bug, not a wording preference** — the classification is reading a string
the OS localizes.

**Fix**: classify at the source, on `std::io::ErrorKind` and the raw OS error code, and carry
a structured kind through `OpResult::Failed` rather than re-deriving it from prose. `os error
67` is `ERROR_BAD_NET_NAME`; `ErrorKind::PermissionDenied` and `NotFound` cover most of the
rest. The localized text stays, as detail — it is what the user will paste into a search.

### 3.3 The missing dimension: *when*

"What / where / why" are all derivable today. **"When" is not** — nothing on a `JobSpec` says
whether it was started by session restore, by a keypress, or by an automatic refresh.

Proposal: `JobSpec.origin`, defaulted so no existing call site changes.

```rust
pub enum JobOrigin {
    /// Restoring saved tabs at startup — the user has operated nothing yet.
    SessionRestore,
    /// A direct consequence of a keypress.
    UserAction,
    /// An automatic re-read after a file operation.
    Refresh,
}
```

This is the field that lets the dialog say "while restoring your session", which is the
difference between an alarming error and an explicable one. It is also reusable: §2.3's
task-panel threshold could exempt `SessionRestore` reads from the quiet period, since at
startup there is nothing else to look at.

### 3.4 Proposed dialog

```
┌Directory unavailable──────────────────────────────────────────────┐
│                                                                   │
│  Tab 5, right pane — while restoring your session                 │
│                                                                   │
│  \\192.168.11.24\testfol                                          │
│  The network name could not be found. (os error 67)               │
│  ネットワーク名が見つかりません。                                 │
│                                                                   │
│  The share may be offline, or the host unreachable.               │
│                                                                   │
│         [ Retry ]   [ Open parent ]   [ Dismiss ]                 │
│                                                                   │
└───────────────────────────────────────────────────────────────────┘
```

Four slots, one per question the user asked for:

| slot | source |
|---|---|
| **what** — the title names the failure class | structured error kind (§3.2), not substring matching |
| **where** — "Tab 5, right pane" | `requesting_pane` (already done in 7.23) |
| **when** — "while restoring your session" | `JobSpec.origin` (§3.3, new) |
| **why** — the path, the cause, the hint | structured kind → hint table; the localized string kept verbatim underneath |

The path goes on its **own line**, not inside a sentence — it is the single most useful thing
in the dialog and it is the thing most likely to be long enough to wrap.

The triple prefix goes away: the title carries the operation class, so the body never needs
"Read directory failed: Failed to read directory".

### 3.5 Buttons

`[Retry]` and `[Open parent]` turn a dead end into a decision. Both already have machinery:

- **Retry** — resubmit the same `ReadDirectory`. Note this is *not* free of the original
  problem: retrying a dead UNC path blocks the worker for another full timeout. That is
  acceptable (it is a worker, and the user asked), but the button must not be the default
  focus, or `Enter`-to-dismiss becomes `Enter`-to-hang-again.
- **Open parent** — `ResolveFallbackPath` already computes exactly this (7.23). When it found
  nothing, the button is disabled or absent; when it found something, this dialog should
  arguably not have appeared at all.

**Default focus goes to `Dismiss`.**

### 3.6 Interaction with 7.23

7.23 made a failed pane read defer its modal to `ResolveFallbackPath`, so the dialog now only
appears when *nothing in the chain is readable* — the genuinely unrecoverable case. That means
this dialog is rarer and more serious than it was, which strengthens the case for buttons over
a bare OK, and weakens the case for `[Open parent]` (by construction there usually isn't one).

Build §3.2 (structured error kinds) first: it is a real bug, it is independently useful, and
both the title and the hint depend on it.

## 5. Notes for whoever picks this up

- **`with_requesting_pane`'s parameter is named `tab_idx` and receives a tab id.** Rename it
  while you are in there; it is one word and it is currently a trap.
- **`ReadDirectory` completion has a `requesting_pane: None` fallback path** that matches
  panes by location and updates *every* tab whose pane sits on that path. Registering reads
  in `background_jobs` does not change this, but be aware it exists before adding another
  producer of `requesting_pane: None` reads.
- **`CompleteJob` finds its spec via `self.jobs.active.get(job_id)`.** A job submitted without
  `JobManager::start_job` completes into nothing — no pane update, no dialog, no cache
  insert. `App::submit_job` (7.23) is the only correct way to submit; do not reintroduce a
  bare `pool.submit_job`.
- **The render path may not touch the filesystem.** Enforced by
  `the_render_path_does_not_touch_the_filesystem` in `rwf-bin/tests/repo_contracts.rs`. If a
  new preview or hint needs a fact about a file, compute it in a job and read it from
  `AppState` — see `JobKind::CountDirectoryEntries` and `SuccessData::JumpCandidates`.
- **Recording a bundle for this**: the startup window is before any keybinding can be pressed,
  so use `RWF_DIAGNOSTICS=1 rwf` rather than `F12`. Bundle `20260910-203646` only caught the
  tail of the wait because `F12` was pressed while it was still running.

## Implementation notes (2026-09-11)

### Piece 1 — structured error kinds (`rwf-lib/src/job/failure_kind.rs`)

`FailureKind` { `NotFound`, `PermissionDenied`, `NetworkUnavailable`, `TimedOut`,
`InvalidPath`, `Other` }, classified from the raw OS code first (a small table for the SMB
codes std leaves `Uncategorized`: 51, 53, 54, 59, 64, **67**, 1203, 1222, 2250 on Windows;
`EHOSTDOWN` on Linux/macOS), then `io::ErrorKind`.

**Departure from §3.2: the kind is not carried through `OpResult::Failed`.** That variant is
built from a `String` at ~80 sites (39 in the executor). Instead `FailureKind::classify(msg)`
recovers the code from std's `(os error N)` suffix — appended by std, never localized, and
preserved verbatim by every `format!("{e:#}")` — and classifies it exactly as an `io::Error`
would be. Only a message with no code falls back to words, and those are rwf's own English
strings or std's kind descriptions, neither translated. `std_still_formats_os_errors_with_their_code`
fails first if std ever changes the suffix. `Dialog::from_job_failure_in` now titles by
`FailureKind` (existing titles kept; new: *Network Location Unavailable*, *Timed Out*).

### Piece 2 — reads in `background_jobs`, id-keyed (option **b**)

- `AppState::track_directory_read`, called from `App::submit_job`, registers every
  `ReadDirectory` as a **quiet** background job named `Read <path>`, under the requesting
  pane's tab **id** (the active tab's for a `requesting_pane: None` refresh).
- `background_jobs` is id-keyed everywhere: the four `app.rs` registration sites and both
  `job_management.rs` ones pass `current_tab().id`; `tab_bar.rs` asks by `tab.id`; the
  `[Tab N]` log text and the job manager's detail resolve id → position via
  `AppState::tab_number` (`?` / "(closed)" once gone). `CloseTab` already filtered by id, so
  it was cancelling nothing for index-registered jobs — now consistent.
- `with_requesting_pane`'s parameter renamed `tab_idx` → `tab_id`.
- **Found while wiring it: `AcknowledgeCancel` never told `background_jobs`.** Harmless when
  only user-started jobs registered; with reads registered, every read superseded by
  navigation would have spun its tab forever. It now marks the job cancelled.

### Piece 3 — quiet period

`QUIET_JOB_ANNOUNCE_AFTER = 500 ms`, timed from `Job::started_at` (when a worker picked the
job up — the "existing timing" §2.3 asked to reuse), so a read queued behind busy workers is
not called slow. A quiet job logs nothing at start; `AppState::quiet_jobs_due()` is polled
once per loop iteration and, only when non-empty, fires `Transition::AnnounceQuietJobs`,
which writes `Read <path>: Started` once. After that the job logs `[OK]`/`[FAIL]` like any
other; an unannounced one logs only a failure. **Departure:** `SessionRestore` reads are
*not* exempted from the quiet period (§3.3 suggested it could be). Ten `Started` lines plus
ten `[OK]`s at every launch would bury the one stuck read; the spinner already covers the
startup case immediately.

### Piece 4 — `JobSpec.origin`

`JobOrigin` { `SessionRestore`, `UserAction` (default), `Refresh` }, `JobSpec::with_origin`.
Set by `trigger_initial_directory_reads` (restore) and the `panes_to_refresh` loop (refresh);
the `ResolveFallbackPath` job inherits the failed read's origin so the dialog can use it.

### Piece 5 — the dialog (`ReadFailureDialog`)

`DialogContent::ReadFailure`, raised where the fallback search found nothing. Title
`FailureKind::read_title()`; body: "Tab 5, right pane — while restoring your session", the
path on its own line (middle-truncated), the OS text with the backend's "Failed to read
directory <path>: " removed, and `FailureKind::hint()`. Buttons `[Retry]  [*Dismiss*]`,
focus on Dismiss (`frame.rs` gained `default_button_index`). Retry →
`Transition::RetryPaneRead { tab_id, side }`, which re-reads that tab's pane (not
necessarily the active tab) and sets `is_loading` + `active_job_id`.

**Departures:** no `[Open parent]` — by construction the dialog only appears when
`ResolveFallbackPath` found *no* readable ancestor (§3.6 already predicted this). And a
fallback whose tab closed meanwhile logs `[FAIL]` to the task panel instead of raising a
modal with no pane to retry into.
