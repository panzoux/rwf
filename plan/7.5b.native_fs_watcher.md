# Phase 7.5b — Native Filesystem Watcher as a Poll Trigger

**Created**: 2026-09-17
**Status**: `[-]` **Deferred — not implemented until there is a need** (decided 2026-09-17).
The 7.5 design is considered complete *as a polling method*. The order now is: test that 7.5
works on real hardware → measure it → judge how it feels in daily use (7.5 §4). Revisit this
only if that shows a real problem polling cannot fix (e.g. change latency or idle I/O on large
local folders). Not designed in detail; kept as a record of the idea and its risks.
**Depends on**: [7.5 background polling](7.5.background_polling.md) (implemented; its manual
checks in §4 come first, because their measurements decide whether this is worth doing).
**Partly reverses**: the 2026-05-24 decision recorded in
[docs/ARCHITECTURE.md — ペイン更新機構](../docs/ARCHITECTURE.md) and the ROADMAP "Declined"
row that rejected `notify` outright.

---

## Why this exists

7.5 detects outside changes by re-reading the visible panes on a timer. That is the right
answer where OS change notifications are unreliable (network shares, removable media, WSL),
and it is the rescan half of the design every notification-based file manager ends up with
anyway: notifications are lost on overflow (`inotify` queue, `ReadDirectoryChangesW` buffer),
editors save via temp-file + rename, and network file systems may not notify at all — so an
event can only ever mean "this directory may have changed; re-read it".

What polling costs on **local fixed drives**, where native events work well:

- **Latency** — a change appears after up to one interval (1 s default), not at once.
- **Steady I/O** — every visible pane is re-read, sorted and compared every interval even
  when nothing changed. A folder large enough to list in over 1 s backs its drive off to
  4 s (7.5 D10b), so large local folders get the laggiest updates exactly where a watcher
  would be cheapest.

`lf` (`watch` option, fsnotify) and `yazi` (file change watching, not on inactive tabs,
PollWatcher fallback on WSL / NetBSD) both use native events with the same rescan-on-event
shape.

## Shape of the change

The trigger is the only missing piece. Everything after it is 7.5, already built and tested:

```text
native watcher (local fixed drives only, non-recursive, visible panes of the active tab)
   │ any event / overflow / error for a watched directory
   ▼
mark that pane due now            ← same mechanism as Transition::TerminalFocusGained (7.5 T5)
   ▼
PollTick → ReadDirectory on the poll pool → stale-result checks (D12) →
apply_directory_listing (cursor by name, sizes carried) → failure split (D9)
```

- Events are never turned into listing diffs; the re-read is the truth.
- The watch set follows `visible_panes()`; re-register on navigation, tab switch, viewer
  layout change. Inactive tabs are not watched.
- Bursts coalesce for free: a pane already polling is skipped, and one poll per pane is in
  flight at most.
- Overflow / watcher error → mark the pane due (a normal full re-read), and keep a **slow
  safety-net poll** (e.g. 30 s) on watched panes for missed events.
- Drives that are not local-fixed keep 7.5 polling unchanged, including back-off, automatic
  switch-off and `[no poll]` / `[offline]`.
- Layer 1 refreshes after rwf's own jobs stay: they are immediate, and D12 already protects
  them from stale reads. The watcher will also report rwf's own changes; that costs one
  redundant, usually "unchanged" read.

## Must be verified before committing to it

1. **Windows handles.** `ReadDirectoryChangesW` holds an open directory handle. Check on real
   hardware whether it blocks *Safely Remove* of a USB stick, or rename/delete of the watched
   folder (or its parents) from Explorer. If it does, removable drives must never be watched,
   and the handle must be dropped before rwf itself renames/deletes a watched folder.
2. **Drive classification** (fixed / removable / network / WSL) must run as a job — it can
   block on network paths ([IMPLICIT_CONTRACTS §8](../docs/IMPLICIT_CONTRACTS.md)).
3. **Where events arrive.** The watcher's callback thread must only send a message; turning it
   into a transition happens in the App loop, which must be woken for it (today it sleeps on
   `crossterm::event::poll`).
4. **Measured benefit.** Record from the 7.5 manual checks: CPU and change latency with a large
   local folder (e.g. 20k entries) under polling. If both are acceptable, this item may be
   declined instead.

## Open questions

- Keep the per-drive interval at `PollingIntervalMs` for watched panes, or only the safety net?
- Config surface: a switch to force polling everywhere (e.g. `PollingMode: "Auto" | "Poll"`)?
- Linux `inotify` watch limits are irrelevant at two non-recursive watches, but WSL paths under
  `/mnt/c` need the polling fallback — detect via the mount table 7.5 already loads.
