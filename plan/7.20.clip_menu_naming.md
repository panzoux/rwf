# Phase 7.20 — Clip Menu Naming & Menu Descriptions (クリップメニューの命名整理)

**Created**: 2026-09-10
**Status**: **Implemented — all four §7 pieces done (2026-09-11).** Pieces 2–3 (the rename)

**Origin**: diagnostic bundle `20260910-004934`. The reported bug ("all clip* menus fail")
is fixed separately (see `plan/ROADMAP.md` 7.23); this document covers the second half of

> §3 is the mechanism that makes short labels safe (descriptions shown beside them);
> build it **first**, per §7. §6 is the hand-migration the developer's own

## Executive Summary

The `F6` clip menu asks the user to decode three independent axes from bare labels, and the
labels encode them inconsistently. Meanwhile every function already carries a `Description`
that says exactly what it does, and the menu renders only the `Name`.

Two changes, together:

1. **Rename** the seven `ClipText` functions and the two menu functions onto one consistent
   scheme, and rename `menu_copy_paths.json` to match the vocabulary it uses.
2. **Show the description** next to each menu item, resolved once at config load.

Neither is useful alone. Renaming alone still has to fit the whole meaning into ~25 characters
— which is what failed the first time. Descriptions alone leave `clip path` and
`clip file path` sitting next to each other meaning different things.

**Scope note**: shipped resources and repo docs only. `--export-config-files` uses
`write_if_absent`, so no existing installation is touched; the migration table in §6 is for
the user to apply by hand.

## 1. What is actually wrong with the names

### 1.1 Three axes, inconsistently encoded

Every clip entry is a point in a three-axis space:

| axis | values |
|---|---|
| **what** | the entry's name / the entry's full path / the pane's directory |
| **which** | the cursor entry / every marked entry |
| **form** | bare / double-quoted |

The current names encode them like this:

| current name | what | which | form |
|---|---|---|---|
| `clip file name` | name | cursor | bare |
| `clip file path` | full path | cursor | bare |
| `clip path` | **directory** | cursor | bare |
| `clip marked file path` | full path | marked | bare |
| `clip marked file name` | name | marked | bare |
| `clip "file path"` | full path | cursor | quoted |
| `clip "path"` | directory | cursor | quoted |

Three specific failures:

- **`clip file path` vs `clip path`.** One word apart, and that word changes the *what* axis
  from "this file's absolute path" to "the directory the pane is showing". This is the single
  worst pair in the menu and the one the report was written about.
- **Quoting is spelled with literal quote characters.** `clip "file path"` reads as emphasis
  or as a quotation, not as "the output will be wrapped in double quotes". It also sorts and
  char-jumps badly.
- **`file` carries no information.** It appears in four of seven names and never
  distinguishes anything — the axis it looks like it marks (*which*) is actually marked by
  `marked`.

### 1.2 "clip" vs "copy" — three vocabularies for one thing

| where | word used |
|---|---|
| function names | `clip …` |
| menu function `menu_clip_paths` | `clip` |
| the file it loads, `menu_copy_paths.json` | `copy` |
| its description, "Show copy-paths menu" | `copy` |
| the `C` / `c` keybinding | `Copy` — **the file-copy operation** |

`copy` is already taken by file copy. `clip` is the word that does not collide, so it should
be the only word used.

### 1.3 Two naming styles in one list

`menu_clip_paths` and `menu_config` are snake_case identifiers; every other function is
lowercase prose (`clip file path`, `edit config file`, `fzf jump to file`). There is no reason
for the split — keybindings already invoke prose names directly:

```json
"F4": { "InvokeCustomFunction": "fzf jump to file" }
```

### 1.4 The clear text exists and is not shown

Every function already has a `Description` that is better than its `Name`:

| Name | Description |
|---|---|
| `clip file path` | Copy the cursor file's full path |
| `clip path` | Copy the active pane's directory |

`CustomFunctionMenuDialog` holds `Vec<MenuItem>`, and `MenuItem` is `{ name, action }`. The
description lives on the `CustomFunction` that `action` names, and never reaches the renderer.

## 2. Proposed naming scheme

**Rules** (revised 2026-09-10 after review):

1. **The menu title is the verb.** The menu is titled `clip`, so repeating `clip` on every
   line is pure redundancy — seven labels that all start with the same word carry no
   information in their first word and push the distinguishing part rightwards.
2. `full path` always means an entry's absolute path; `current directory` always means the
   pane's directory. The `path` / `file path` pair is retired.
3. **`directory`, not `folder`.** rwf is a TUI for people who left GUI file managers; the
   Unix vocabulary is the one they read fluently. This makes `fzf jump to dir` the odd one
   out — `dir` there is an abbreviation of the same word, so it stands.
4. `marked` appears in the *name*, not only in the description. Items must never differ from
   one another by a plural `s` alone.
5. Everything is lowercase prose. No snake_case identifiers.
6. **Quoted variants leave the menu** — see §2.4.

### 2.1 The clip functions

| # | current | proposed label | template | description shown beside it |
|---|---|---|---|---|
| 1 | `clip file name` | `file name` | `$F` | the cursor entry's name |
| 2 | `clip file path` | `full path` | `$P$/$F` | the cursor entry's full path |
| 3 | `clip path` | `current directory` | `$P` | the active pane's directory |
| — | — | *separator* | — | — |
| 4 | `clip marked file name` | `marked file names` | `$MFL` | every marked entry's name, one per line |
| 5 | `clip marked file path` | `marked full paths` | `$MPL` | every marked entry's full path, one per line |

Templates are unchanged. Function `Name` and menu-item `Name` stay identical to each other,
as they are today.

**Two deviations from the reviewed wording, both flagged in §8:**

- `current directory`, not `current directory name`. Next to `file name` — which means the
  basename — "directory name" reads as *the directory's basename*, but the template is `$P`,
  the full path. See §8.2; if the basename really is wanted, that is a **new macro**, since
  none of `$P`/`$F`/`$O` yields it.
- `marked full paths`, not `marked paths`, so the marked pair mirrors the singular pair
  (`full path` → `marked full paths`).

Descriptions are reworded from imperative ("Copy the cursor file's name") to a noun phrase,
because they are read *under the menu's own title* rather than as standalone sentences — the
title already said "clip", and so does the label's neighbour:

```
file name          the cursor entry's name
```

not

```
file name          Copy the cursor file's name
```

"file" becomes "entry" throughout: these macros work on directories under the cursor too.

### 2.2 Menu functions and the menu file

| kind | current | proposed |
|---|---|---|
| function | `menu_clip_paths` | `clip menu` |
| function | `menu_config` | `config menu` |
| resource | `rwf-lib/resources/default_menu_copy_paths.json` | `default_menu_clip.json` |
| exported file | `menu_copy_paths.json` | `menu_clip.json` |
| description | "Show copy-paths menu" | "the clip menu" |

`paths` is dropped from the menu name because the menu also holds names, not only paths.
The menu title is what supplies the verb for every line (rule 1), so it must stay short and
must stay `clip`.

### 2.3 Resulting menu

```
┌clip──────────────────────────────────────────────────────────────┐
│  file name             the cursor entry's name                   │
│  full path             the cursor entry's full path              │
│  current directory     the active pane's directory               │
│  ─────                                                           │
│  marked file names     every marked entry's name, one per line   │
│  marked full paths     every marked entry's full path, one per … │
│ [Enter] Execute  [Esc] Close                                     │
└──────────────────────────────────────────────────────────────────┘
```

Five lines instead of seven, and the distinguishing word is now the first word on each line —
which is also what the menu's char-jump keys match on, so typing `m` reaches the marked
entries and `c` the current directory.

### 2.4 Quoted variants: keys, not menu slots

The two quoted entries leave the menu. They stay as `ClipText` functions, so a user who wants
them binds a key:

```json
"Ctrl+F6": { "InvokeCustomFunction": "full path, quoted" }
```

This is the point of `ClipText` being a function rather than a menu feature: it is already
directly bindable, and anything directly bindable does not need to consume a menu slot. A
user who prefers them in the menu adds two lines to `menu_clip.json` — the mechanism is
unchanged, only the shipped default is shorter.

**Quoting stays in the template — it must not become a modifier.** The tempting alternative
is a "quote the result" modifier (`Shift+Enter`, a config flag) applied to whichever clip
runs. Rejected: the templates for these two entries already contain literal quotes
(`"$P$/$F"`), so a modifier applied to them yields `""C:\x""` — double-double-quoting. Making
the modifier idempotent means inspecting the expanded text for existing quotes and guessing
intent, which is worse than two extra functions.

**Known edge case, not fixed here.** `"$P$/$F"` wraps the path in quotes by string
concatenation, so a path *containing* a double quote produces malformed output. `"` is
illegal in Windows filenames, so this cannot occur on the primary platform; it can on
Linux/macOS. A real fix is a shell-quoting macro (escape inner quotes) rather than a template
that spells the quotes literally. Recorded as future work, not scoped here.

## 3. Showing descriptions

### 3.1 Where to resolve — chosen: at config load

**Chosen: resolve in `resolve_menu_files`** (`rwf-lib/src/model/dialog/mod.rs`).

That function already exists to turn `Menu: "filename.json"` into an item list, and it already
holds the whole `&mut [CustomFunction]` slice. Build a `name → description` map first, then
fill in any item whose description is absent.

- One pass, at load. Nothing per frame, nothing per keystroke.
- The renderer *and* the width calculation both just read a field — no plumbing of
  `&[CustomFunction]` into the render layer.
- Users get a per-item override for free (see §3.2).

**Rejected: resolve at render time.** Passing `&[CustomFunction]` into
`render_custom_function_menu` looks smaller, but `dialog_width` and `dialog_height` in
`ui/dialog/mod.rs` also need the description to size the box, so the slice has to be threaded
into the geometry functions too — and the lookup then runs on every frame.

### 3.2 Model change

```rust
#[derive(Debug, Clone, Default, PartialEq, serde::Serialize, serde::Deserialize)]
#[serde(rename_all = "PascalCase")]
pub struct MenuItem {
    pub name: String,
    /// Custom function name or built-in action name. Empty string = separator.
    #[serde(default)]
    pub action: String,
    /// Shown dimmed beside the name. Filled from the target function's own
    /// description when the menu file does not give one, so the common case
    /// needs no extra JSON.
    #[serde(default)]
    pub description: Option<String>,
}
```

`MenuFile` already carries `#[serde(rename_all = "PascalCase")]`, so on disk this is
`"Description"`, and `#[serde(default)]` keeps every existing menu file loading unchanged —
both halves of the serialization contract that `rwf-bin/tests/config_contracts.rs` guards.

An explicit `Description` in the menu file wins over the function's own, so a user can label
one entry differently in one menu without touching the function.

**Cost to flag:** `MenuItem` is built with struct literals across the snapshot tests and
elsewhere; a third field breaks all of them. Add `MenuItem::new(name, action)` and migrate the
literals in the same change. `Default` is derived so future fields do not repeat this.

### 3.3 Rendering

Two columns in `render_custom_function_menu`: name left, description right in a dimmed style
taken from `rwf-bin/src/ui/dialog/common.rs` — **no new inline `Style::default().fg().bg()`
chains** (quality rule 4).

Column budget:

1. Name column = widest selectable item's **display width**.
2. Description gets the remainder, minus a two-space gutter.
3. If the remainder is under ~20 columns, **drop the description column entirely** rather than
   truncating it to noise. Names alone must stay readable on a narrow terminal.
4. Otherwise truncate with `unicode_utils::truncate_to_width`.

Separator rows (`-----`, empty action) have no description and render as they do today.

### 3.5 Editing a menu file takes effect on config reload

Because descriptions are resolved at load, editing `menu_clip.json` or a function's
`Description` needs a config reload to show up — `Z` (`ReloadConfig`), or "reload config" in
the config menu. **Verified**: `Transition::ReloadConfig` (`rwf-lib/src/state/mod.rs:1248`)
calls `load_custom_functions`, which ends in `resolve_menu_files`
(`model/dialog/mod.rs:2352`), so the fill re-runs on every reload with no extra wiring.

This is the same reload the user already needs after editing any custom function, so it adds
no new step — but it is the one behavioural consequence of choosing load-time over
render-time resolution, and it belongs in the user guide next to the `ClipText` section.

### 3.4 A pre-existing width bug this uncovers

`ui/dialog/mod.rs` sizes this dialog with:

```rust
.map(|i| i.name.len())     // bytes, not display columns
```

A Japanese menu name already mis-sizes the box today, and the project rule is explicit —
never measure or slice by byte index; use `rwf-bin/src/ui/unicode_utils.rs`. Since this
formula is being rewritten for the second column anyway, fix it to display width in the same
change. The same `.len()` pattern is a few lines below in the `OpenWithPicker` arm; fixing
that one too is cheap and is called out as optional in §7.

## 6. Migration — the user applies this by hand

`--export-config-files` uses `write_if_absent`, so **nothing in `%APPDATA%\rwf\` is touched by
this change**. An existing installation keeps the old names indefinitely.

To adopt the new names, edit two files **together** — `Action` strings are function `Name`
lookups, so changing one file alone silently breaks every entry:

**`custom_functions.json`** — the `Name` field of 9 entries:

```
menu_clip_paths        → clip menu
menu_config            → config menu
clip file name         → file name
clip file path         → full path
clip path              → current directory
clip marked file name  → marked file names
clip marked file path  → marked full paths
clip "file path"       → full path, quoted
clip "path"            → current directory, quoted
```

**`menu_copy_paths.json`** (rename to `menu_clip.json`) — both `Name` *and* `Action`, using
the same mapping. **The two quoted entries are deleted from the menu file** (§2.4); the
functions stay in `custom_functions.json`, so binding a key to them keeps them reachable:

```json
"Ctrl+F6": { "InvokeCustomFunction": "full path, quoted" }
```

**`keybindings.json`** — `"F6"` and `"z"`:

```json
"F6": { "InvokeCustomFunction": "clip menu" },
"z":  { "InvokeCustomFunction": "config menu" }
```

**`custom_functions.json`**, `edit clip menu file` — point its command at `menu_clip.json`.

Descriptions need no editing: the menu reads them from the functions.

## 7. Implementation order — all four pieces are in scope

Decided at review: ship all four. Ordered so each is independently revertable, and so the
first one is useful on its own if the rest slips.

| # | piece | why this order |
|---|---|---|
| 1 | `MenuItem.description` + load-time resolve + two-column render + display-width fix | makes the menu legible with the *current* names, before anyone migrates anything |
| 2 | Relabel the 5 remaining clip entries; move the 2 quoted ones out of the menu (§2.4) | the labels only have to carry half the meaning once piece 1 lands |
| 3 | Rename `menu_copy_paths.json` → `menu_clip.json`, `menu_clip_paths` → `clip menu`, `menu_config` → `config menu` | touches `help_content.rs` / `lib.rs` / `main.rs`; independent of 1 and 2 |
| 4 | Fix the same `.len()` byte-width bug in the `OpenWithPicker` arm | drive-by, same class as the fix in piece 1 |

Piece 1 first is deliberate: it de-risks the rename by giving every item a second,
independent label, so a bad new name is visibly bad before it is the only label there is.

## 8. Open questions

1. ~~`folder` vs `dir`~~ — **resolved: `directory`.** rwf is a TUI for people who left GUI
   file managers; the Unix word is the one they read fluently. `fzf jump to dir` keeps its
   abbreviation of the same word.
2. ~~`current directory` vs `current directory name`~~ — **resolved: `current directory`.**
   Two candidates were considered and both rejected:

   - **`… name`** (either variant) promises a basename. Next to `file name`, which *is* a
     basename, a reader reasonably expects `parent directory name` to yield `rwf` rather
     than `C:\Users\…\rwf`. The template is `$P`, a full path, so the word is actively
     misleading. See the follow-up below.
   - **`parent directory`** collides with vocabulary rwf already owns. `NavigateToParent` is
     bound to `Backspace` in the shipped keybindings, and in every file manager "parent
     directory" means *one level up*. `$P` is not one level up — it is the directory the
     pane is currently showing. The word is correct in the abstract (it is the parent of the
     cursor entry) and wrong in rwf's own terms, which is the worse kind of wrong.

   `current directory` is neither ambiguous about basename-vs-path nor in conflict with an
   existing action, and the description beside it removes any remaining doubt.

   **Follow-up worth having (not scoped here): a basename macro.** No macro yields the last
   segment of `$P`, and it is genuinely useful — naming an archive or a branch after the
   folder you are standing in. If added (say `$PN`), it earns an *additional* entry,
   `current directory name`, sitting under `current directory`. At that point the two labels
   differ by exactly the word that distinguishes them, which is the whole point of §2's
   rules. Recorded in `plan/ROADMAP.md` 7.20 rather than built now.
3. ~~Does the quoted pair earn two menu slots?~~ — **resolved: no.** They become keybindings;
   see §2.4, which also records why quoting must stay in the template rather than becoming a
   modifier (double-double-quoting), and the unfixed `"`-in-filename edge case.

## Implementation notes (2026-09-11, pieces 1 and 4)

What was built, and where it differs from the design text above:

- **`fill_menu_descriptions`** (`rwf-lib/src/model/dialog/mod.rs`) runs at the end of
  `resolve_menu_files`, so it covers menu files *and* inline `Menu: [...]` items, and re-runs on
  every reload. Name lookup takes the first match, like dispatch. An empty `Description` on a
  function is treated as absent.
- **`MenuItem.description`** is `#[serde(default, skip_serializing_if = "Option::is_none")]`
  rather than plain `default` — nothing on disk gains a `"Description": null`.
- **The existing four snapshots did not change.** §4 expected re-approval; it was not needed,
  because an item without a description renders exactly as before.
- **Selected row**: the description keeps the white highlight in a new
  `common::DIALOG_SELECTED_DIM` (dark gray on white), so the highlight is unbroken across the
  row. `DIALOG_DIM` there would have cut a gray band into it.
- §3.3's threshold is `MIN_DESCRIPTION_COLUMNS = 20`, with one addition: a column wide enough
  for every description is always shown, however narrow, so a menu of short descriptions is
  never stripped for failing a minimum it does not need.

Tests: `a_menu_item_takes_the_description_of_the_function_it_names`,
`a_description_given_in_the_menu_file_beats_the_functions_own`,
`an_item_whose_action_names_no_function_keeps_no_description`,
`loading_the_shipped_files_gives_every_clip_menu_entry_a_description` (end to end through
`load_custom_functions` with the shipped resources), and snapshots
`custom_function_menu_with_descriptions` / `_with_cjk_names` /
`_too_narrow_for_descriptions` (80 columns drops the column, 120 truncates it).
